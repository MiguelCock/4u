# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

GPS positioning correction system for assisted navigation of visually impaired users on university campuses. It corrects raw GPS (5-20m error) down to <5m by matching a live phone photo against a database of pre-captured "anchor point" photos (visual embeddings), then fusing that visual correction with GPS and IMU data via a Kalman filter. See `README.md` for the full project rationale, data flow, and development schedule.

This is a Python/Dart monorepo, not a single deployable app — each top-level directory is an independently versioned component with its own `pyproject.toml`/`pubspec.yaml`.

## Repository layout

- `application/` — Flutter mobile app (Dart). Single codebase for both `user` (sends photo+GPS+IMU, receives corrected position) and `admin` (captures anchor points) roles.
- `backend-data-collection/` — FastAPI service that receives images + GPS metadata from the app and persists them via Supabase (Postgres + Storage).
- `backend-ai-training/` — FastAPI service extracting embeddings (pretrained EfficientNet-B0) from anchor-point photos and indexing/searching them in Qdrant (`POST /index_anchor`, `POST /search_similar`); fine-tuning the model remains an offline task, not yet implemented.
- `backend-map-management/` — FastAPI service for the admin view: creating/listing anchor points, buildings, and places (`anchor_points`, `buildings`, `places` tables).
- `backend-route-management/` — FastAPI service for creating and managing user-facing navigation routes (`routes` table).
- `backend-user-management/` — FastAPI service for managing user information and configuration: profile data and preferences (`profiles` table) plus the static `roles` reference table.
- `backend-navigation-management/` — FastAPI service tracking navigation sessions, per-tick GPS/correction logs, and user feedback (`navigation_sessions`, `navigation_logs`, `user_feedback` tables).
- `backend-positioning/` — FastAPI service fusing raw GPS with a visual anchor-point match (from `backend-ai-training`) into a corrected position via an Unscented Kalman Filter (`POST /correct_position`). The first service in this repo to call another service over HTTP. Has no Qdrant credentials of its own; needs Supabase only to verify caller bearer tokens, not for table access.
- `packages/` — Shared Python library (`uv` workspace package, importable as `packages`) wrapping Supabase and Qdrant clients. Consumed by the backend services via `[tool.uv.sources]` path dependencies (see `backend-data-collection/pyproject.toml`), not published. Its purpose is to hold logic shared across backend services (DB/vector-store clients, auth helpers, etc.) so each new service depends on it instead of re-implementing that logic — put cross-service logic here, not in an individual service. `backend-positioning` depends on it only for `SupaBase`'s bearer-token verification (`get_caller_id`), not for table access — it has no Qdrant use at all.
- `db_schema/` — Hand-maintained Postgres/Supabase table definitions (not a migration tool — apply manually). Core entities: `places` → `buildings` → `anchor_points`, plus `profiles`/`roles`, `navigation_sessions` → `navigation_logs`, `routes`, `user_feedback`, `location_type`, `photos` (raw user-walk photo uploads from `backend-data-collection`, unrelated to `anchor_point_photos`). `navigation_sessions`, `navigation_logs`, and `user_feedback` are owned by `backend-navigation-management`.
- `gateway/` — `nginx.conf` for the API gateway (path-prefix reverse proxy) in front of the 7 backend services; not a `uv`/Python component, just config mounted into an `nginx:1.27-alpine` container by `docker-compose.yml`.

Each Python component (`backend-data-collection`, `backend-ai-training`, `backend-map-management`, `backend-route-management`, `backend-user-management`, `backend-navigation-management`, `backend-positioning`, `packages`) is a separate `uv` project with its own lockfile — run `uv` commands from inside that directory, not the repo root.

The backend is split into independent microservices by responsibility (per `README.md`) rather than one monolith. New services should follow the same pattern used by `backend-map-management`/`backend-route-management`: scaffolded with `uv init --app --no-package`, an `app/` package (`main.py`, `models.py`), a `tests/` suite, an editable path dependency on `../packages` (`[tool.uv.sources]`), and registration in the CI workflow's `filters` and `components` (see CI below).

## Commands

### Python backends (uv)

Run from within the specific component directory (`backend-data-collection/`, `backend-ai-training/`, `backend-map-management/`, `backend-route-management/`, `backend-user-management/`, `backend-navigation-management/`, `backend-positioning/`, or `packages/`):

```bash
uv sync                    # install dependencies (creates .venv)
uv run pytest              # run tests
uv run fastapi dev         # run backend-data-collection locally with reload
```

`backend-data-collection` depends on the local `packages` project via an editable path source, so changes in `packages/` are picked up immediately without reinstalling.

Docker: each backend service's `Dockerfile` `COPY`s both its own directory and the sibling `packages/` (for the editable path dependency), so it must be built with the **repo root** as context, not the service directory:
```bash
docker build -f backend-data-collection/Dockerfile -t fastapi-app .   # from repo root
docker run -p 8000:80 --env-file backend-data-collection/.env fastapi-app
```
Or run all 5 backend services together (see `docker-compose.yml` at the repo root):
```bash
docker compose up --build
```

### Flutter app (`application/`)

```bash
flutter pub get
flutter run
flutter test
flutter pub outdated
flutter pub upgrade --major-versions
```

Connecting a physical device over ADB (wireless):
```bash
adb pair IP_ADDRESS:PAIRING_PORT PAIR_CODE
adb connect IP_ADDRESS:ADB_PORT
adb devices
```

## Testing expectations

Every component is expected to carry its own test suite: the Flutter app is tested with `flutter test`, and every Python component (`packages` and each backend service) is tested with `pytest` via `uv run pytest`. When adding a new backend service or extending `packages`, add tests alongside it rather than leaving it uncovered — CI (below) is wired to discover and run these per-component. For standing up every component together against one Supabase project and testing the real signup → admin capture → route → navigation flow end-to-end, see the root `README.md`'s **Local Setup & End-to-End Testing** section.

## CI

`.github/workflows/ci.yml` uses `dorny/paths-filter` to detect which of `application/`, `packages/`, `backend-data-collection/`, `backend-map-management/`, `backend-route-management/`, `backend-user-management/`, `backend-navigation-management/`, `backend-ai-training/`, `backend-positioning/` changed, then runs only the matching test job (`flutter test` or `uv run pytest`) for each. New Python components must be added to both the `filters` and `components` arrays in that workflow to get CI coverage. Note the path filter only triggers a service's tests when that service's own files change — editing `packages/` does not currently re-run the consuming services' test jobs.

## Environment configuration

Each service loads secrets from its own `.env` (see each component's `.env.example`, all gitignored). `backend-data-collection` needs `SUPABASE_URL`/`SUPABASE_SERVICE_ROLE_KEY` and `QDRANT_URL`/`QDRANT_KEY`; `backend-map-management`, `backend-route-management`, `backend-user-management`, and `backend-navigation-management` need `SUPABASE_URL`/`SUPABASE_SERVICE_ROLE_KEY`. `backend-ai-training` needs `QDRANT_URL`/`QDRANT_KEY` plus, as of #24, `SUPABASE_URL`/`SUPABASE_SERVICE_ROLE_KEY` too — not to query Postgres directly for its own data (the app still hands it anchor-point/photo data straight in the request body), but to verify caller bearer tokens / admin role on its write endpoints (see `backend-ai-training/CLAUDE.md`). `backend-positioning` needs no Qdrant credentials at all (it never queries Qdrant directly, only `backend-ai-training` over the Docker Compose network via the plain, non-secret `AI_TRAINING_URL`), but since the Flutter app became `POST /correct_position`'s first real end-user caller it also needs `SUPABASE_URL`/`SUPABASE_SERVICE_ROLE_KEY`, same reasoning as `backend-ai-training` above — auth verification only, no table access of its own (see `backend-positioning/CLAUDE.md`). The **service_role** key (not the publishable/anon one) is required for the Supabase-backed services — these are trusted server-side processes with a single shared Supabase client and no per-request user JWT, so under Row Level Security an `auth.uid()`-based policy would silently filter out every row for every request if the anon key were used (this bit us once: `profiles` has RLS enabled directly in the Supabase dashboard, not captured in `db_schema/profiles.sql`). The service_role key bypasses RLS entirely and has full DB access — it must stay server-side only, in those `.env` files, and never reach the Flutter app or any client-facing surface. The Flutter app itself needs `SUPABASE_URL`/`SUPABASE_PUBLISHABLE_KEY` (Auth) — intentionally the weaker, client-safe key — plus a single `API_GATEWAY_URL` — every backend service (7, now including `backend-ai-training` and `backend-positioning`) is reached through the API gateway (`gateway/nginx.conf`) at its own path prefix, rather than separate base-URL vars/ports. Env vars are loaded via `python-dotenv` (`load_dotenv()`) in Python services and `flutter_dotenv` (`dotenv.load(fileName: ".env")`) in the Flutter app — the app's `pubspec.yaml` declares `.env` as an asset, so CI copies `.env.example` to `.env` before `flutter pub get`/`flutter test` (see `.github/workflows/ci.yml`). `packages` also has its own `.env`/`.env.example` (all four vars) — unlike the other components, its `.env` is expected to hold *real* Supabase/Qdrant Cloud credentials, since `packages/tests/test_supabase.py` and `packages/tests/test_qdrant.py` make live connectivity checks against the actual services rather than mocking them; both skip cleanly if the vars are unset. The same four vars are also set as GitHub Actions repo secrets so CI runs these live checks too (see `.github/workflows/ci.yml`'s `test` job env).

## Architecture notes

- **`packages` client wrappers**: `SupaBase` (`packages/src/packages/supabase.py`) wraps Supabase Storage (photo bucket `"Photo"`, plus a generic `upload_image(bucket, file, filename)` used by `backend-map-management`'s anchor-point photo upload, and its delete-side counterpart `delete_images_by_url(bucket, urls)` — takes public URLs rather than filenames so callers don't each need their own URL-parsing logic, used by `backend-map-management`'s delete endpoints to best-effort clean up photo files when the underlying anchor point/building/place is deleted, see `backend-map-management/CLAUDE.md`), auth (`sing_up`/`log_in`/`is_logged_in` stubs), photo-table CRUD, and a `health_check()` (queries the `roles` reference table — Supabase's `/rest/v1/` introspection root now requires a secret key, so a real table read is the reliable way to prove a publishable-key connection is live), but exposes the underlying `supabase-py` client as `db.client` — services that need a table `SupaBase` doesn't wrap yet (e.g. `anchor_points`, `buildings`, `routes` in `backend-map-management`/`backend-route-management`) call `db.client.table(...)` directly rather than duplicating a wrapper method per table. If the same table access pattern starts repeating across services, promote it into `SupaBase` instead of leaving it duplicated in each service's `app/main.py` — exactly what happened with the per-request auth guard: `get_caller_id` (a FastAPI dependency verifying a Supabase Auth bearer token live) and `is_admin(caller_id)` (checking `profiles.role_id` against `SupaBase.ADMIN_ROLE_ID`) started as a copy-pasted block in `backend-user-management` (#111), got copy-pasted again into 4 more services rolling the same pattern out (#24), and were then pulled into `SupaBase` itself so every service instead does `db = SupaBase(...); get_caller_id = db.get_caller_id` and calls `db.is_admin(caller_id)` — one implementation instead of six near-identical copies. This is also why `packages` now depends on `fastapi` (for `Header`/`HTTPException`), the first non-DB/vector-store dependency it's taken on. `Qdrant` (`packages/src/packages/qdrant.py`) similarly wraps `QdrantClient`, with `health_check()` and `ensure_collection(name, vector_size, distance)`; `backend-ai-training` is now its real caller (`POST /index_anchor`/`POST /search_similar`, collection `anchor_point_photos`, see `backend-ai-training/CLAUDE.md`) — previously only its own test file exercised it.
- **New backend services (`backend-map-management`, `backend-route-management`)**: currently CRUD-stub level, mirroring `backend-data-collection`'s style — a `GET /` health check plus per-resource create/list/get endpoints that talk straight to Supabase tables, no business logic (route computation, anchor verification workflow, etc.) implemented yet. Tests use `fastapi.testclient.TestClient` against the FastAPI `app` object; `tests/conftest.py` sets dummy `SUPABASE_URL`/`SUPABASE_SERVICE_ROLE_KEY` env vars before import so `pytest` doesn't need real credentials or network access — only the `/` route is safe to assert against without hitting Supabase for real, since the client is created eagerly at module import time.
- **Flutter app structure**: `main.dart` loads `.env`, initializes Supabase Auth, loads `flutter_localizations`/generated `AppLocalizations` (English/Spanish, see Internationalization below), and shows `AuthGate` (`lib/auth/auth_gate.dart`), which routes to `LoginScreen`/`SignupScreen` when signed out, or `UserHomeScreen`/`AdminHomeScreen` (by `profiles.role_id`) when signed in. `UserHomeScreen` (`lib/user/`) *is* the Uber-style trip-planning flow directly, not a map and not a FAB into a separate screen: the user picks only a destination (`anchor_point_picker_screen.dart`'s University → Building → anchor-point drill-down) - the start point is auto-selected as the verified anchor point nearest their live GPS fix (`lib/services/geo_utils.dart`) - then `backend-route-management`'s `POST /routes/find_or_create` finds or computes a route into `navigation_screen.dart`. A gear icon opens `settings_screen.dart` (verbosity/high-contrast/language, backed by `profiles.preferences`); a secondary app-bar icon opens the original raw camera-capture prototype (`SimpleCameraWidget`, `camera.dart` — uploads to `backend-data-collection`, a distinct feature), not the default view anymore. `LocationService` (`lib/services/location_service.dart`) still exposes a broadcast `Stream<Position>` and cached `lastPosition` that any widget can subscribe to independently, plus a `lastError` (`LocationError` enum) so permission-denial states have a real, recoverable UI instead of an infinite spinner. `AdminHomeScreen` (`lib/admin/`) is a 5-tab screen — Universities/Buildings/Anchor points/Connections (`GET /anchor-points` etc., opening `capture_screen.dart` via a floating action button) plus **Users** (`GET /profiles`, promote/demote via `PATCH /profiles/{id}`) — with a drawer entry into `live_sessions_screen.dart`/`session_tracking_screen.dart` for watching an active navigation session's live trail. `lib/services/api_service.dart` provides one HTTP client class per backend service (`UserManagementApi`, `MapManagementApi`, `RouteManagementApi`, `NavigationManagementApi`, `DataCollectionApi`, `AiTrainingApi`, `PositioningApi`), each built by appending its own fixed path prefix to the single `API_GATEWAY_URL` from `.env` — screens use these instead of inlining `http` calls or reading env vars themselves.
- **Internationalization**: Flutter's official `flutter gen-l10n` (`application/l10n.yaml`, ARB files in `application/lib/l10n/`) generates `AppLocalizations` for English (source) and Spanish. Fully localized: the auth screens, `location.dart`/`camera.dart`, and every `lib/user/` screen. Deliberately not yet localized: the older admin CRUD screens (place/building/anchor-point/connection forms) - tracked as an explicit follow-up rather than silently incomplete, since translating ~20 screens' worth of strings in the same change that wired up the infrastructure was explicitly scoped out (see `application/CLAUDE.md`).
- **API gateway**: `gateway/nginx.conf` is a path-prefix reverse proxy (an `nginx:1.27-alpine` container in `docker-compose.yml`) in front of the 7 backend services — the app, and any other future client, only ever talks to one URL. Route inventories across the services are disjoint except each one's own `GET /` health check, so prefix-stripping (`/map/anchor-points` → `map-management`'s `/anchor-points`) works with no path rewriting surprises. The backend services are no longer individually host/LAN-exposed by `docker-compose.yml` — only the gateway's port (8000) is published; running a service standalone via `uv run fastapi dev` for isolated debugging still works and bypasses the gateway entirely.
- **Data flow today**: `camera.dart`'s photo upload now goes through `DataCollectionApi().postMultipart(...)` (fixed alongside the API gateway work — it used to hardcode a URL rather than reading any config at all).
- The embedding-extraction/Qdrant indexing-search half of the root `README.md`'s pipeline (`backend-ai-training`'s `POST /index_anchor`/`POST /search_similar`) and the Kalman-filter fusion half (`backend-positioning`'s `POST /correct_position`, fusing GPS + a visual anchor-point match) are both real now. Scoped to **GPS + visual only, not GPS + IMU + visual** as the README originally described — no IMU (accelerometer/gyroscope) capture exists anywhere in the app (see `backend-positioning/CLAUDE.md`). `NavigationScreen` now calls `/correct_position` on a 1s-floor loop and forwards its result into `backend-navigation-management`'s `POST /logs` (see `application/CLAUDE.md`). Don't assume README-described endpoints exist beyond what's documented per-service; check the actual source.
