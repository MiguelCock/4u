# 0.6 stories

Everything planned for the 0.6 release. Stories are medium-sized: each takes one to four components that can reasonably be done together. They have no dates; the groups are in the order to start them. Each one is also a GitHub issue in the `0.6` milestone.

**How to read a story's "From notes":** the numbers point to the [coverage table](#coverage-every-request-mapped-to-a-story), which lists every request made for this release and the story that takes it. **"Needs you"** is what only the project owner can provide.

Every story also has to meet the [definition of done](#definition-of-done).

## Definition of done

Every story, on top of its own "done when":
- **Older apps keep working:** backend changes are additive, as `CLAUDE.md` requires.
- **Tests** for what changed, and CI green.
- **Strings** in English and Spanish.
- **`CHANGELOG.md`** updated, and the docs of whatever changed, including the relevant `CLAUDE.md`.
- **Screenshots retaken** when an admin screen changes (`docs/admin-guide/tools/`), with the numbered tables still matching.
- **No personal or health details** from tests in the repo or issues. Test notes stay in the local `test_users_comments/`.

## A. Event readiness

The event is at EAFIT, with about 10 people on the standard user flow, on the AWS Academy lab. Before it, many admins will be improving the map at the same time. Server-side work here needs no app release, so it can go live on its own, even if the rest of 0.6 isn't ready.

### A1 · Load test and baseline (#173)

**Problem.** Nobody knows how many people the app can serve. The only figures are from one user at a time, and the 8-person limit above is an estimate. Admins matter too: verifying a point runs the photo model in the service users' searches need, and every admin screen reads five whole lists.

**Scope.**
- A tool (`loadtest/`) that simulates people on a trip and admins editing in a sandbox, never touching real data: real photos and GPS through `POST /correct_position`, plus the trip's logs and route calls, at the pace a phone sends them.
- Photos come from the frames stored by admin test walks (the `navigation-frames` bucket), so they're real campus pictures.
- Runs at 5, 10, 15 and 20 people, at 5 and 10 admins, at 10 people plus 5 admins, and 10 people for 30 minutes, reporting p50, p95 and errors per endpoint, and the point where it stops keeping up.
- Reports CPU and memory on the server, and CPU credit use, since t3 machines slow down when credits run out.
- Saved results, to compare every later change against.
- Splits the time into model, Qdrant, Supabase and our own code. Qdrant and Supabase are outside services whose limits or plan may cap the event, whatever our machine is.

**Components:** load test tool, backend-positioning, backend-ai-training.

**Done when:** one command gives the numbers above against the deployed server, the baseline matches real trips, cleanup leaves real data unchanged, and the results and decisions for A2 and A3 are in `docs/loadtest/`.

**Tested by:** its own tests against a stub, including that every write is allowed; then a short smoke run. It doesn't run while people are testing.

**Depends on:** nothing.

**Needs you:** a window of about 1.5 hours when nobody is testing or editing; fresh AWS credentials; telling admins they may briefly see "Prueba de carga".

**From notes:** N24, N25, N42, N44, N57, N64.

### A2 · Position correction under load (#174)

**Problem.** Photo search is slow, and when requests pile up every user waits. An overloaded correction shouldn't stop guidance, because guidance already works from GPS alone.

**Scope.**
- Limit how many photo searches run at once in backend-ai-training.
- Map indexing mustn't starve users' photo search: verifying points waits its turn when users are searching.
- When busy, backend-positioning answers quickly with the GPS-based result instead of queuing, and says so in the response.
- The app sends fewer photos when told the server is busy, and goes back to normal after.
- Review the gateway's per-user and per-address limits for a whole event on one Wi-Fi address.
- **The server's part has to be enough alone.** The phone's part needs the new APK, so anyone on an older version still has to be served well.

**Components:** backend-ai-training, backend-positioning, application, gateway.

**Done when:** at 10 people, with room up to 15, and with admins working at the same time: photo answers p95 ≤ 3 s, other calls p95 ≤ 1 s, errors under 1%, and guidance never stops, even if some get fewer photo corrections. These targets are proposed; confirm or change them with A1's numbers.

**Tested by:** A1 before and after; unit tests of the busy behavior; older app versions keep working, since the response only gains a field.

**Depends on:** A1.

**Needs you:** confirming the targets.

**From notes:** N42, N43, N44, N64.

### A3 · Load balancing on what Academy allows (#175)

**Problem.** One small machine runs everything. A2 protects users, but serving more people needs more CPU.

**Scope.**
- Check which machine sizes and how many machines the Academy lab allows.
- Use the result: a bigger machine, and/or a second one only for photo search, with the gateway balancing between them.
- Compose and deploy changes to match, with secrets staying off the repo.
- **Only photo search can simply be duplicated.** backend-positioning keeps each trip's filter in memory, so a second copy would lose it mid-trip. It stays single, unless the filter moves somewhere shared, or requests stick to one copy.
- Check whether Qdrant's and Supabase's plans cover the load, and upgrade or reduce their use if not.

**Components:** deployment, docker-compose, gateway.

**Done when:** A1 shows the target is met, or we know exactly what limits it and what the fallback is.

**Tested by:** A1 against the new setup; a test of one search machine failing during load.

**Depends on:** A1, A2 helps.

**Needs you:** checking in the AWS Academy console what the lab allows; any paid plan decision.

**From notes:** N24, N31, N32, N43, N44.

### A5 · Many admins editing at once (#201)

**Problem.** Many admins will improve the map at the same time. Today the last save silently wins, other admins' screens go stale until they reload, and each reload reads five whole lists.

**Components:** application, backend-map-management.

**Done when:** two admins editing the same point never silently lose an edit, and the reload cost A1 measures is down.

**Needs you:** two admins to try it.

## B. Measure what fails

### B1 · Anchor point spacing experiment (#177)

**Problem.** The main suspect for the poor Icesi results is points placed too far apart, compared with the closer spacing that worked at EAFIT. It needs measuring, so the limits come from evidence.

**Scope.**
- **Offline:** thin EAFIT's route to about 4–5 m, 8 m and 12–15 m and replay logged walks (`backend-positioning/scripts/replay.py`) on copies, never changing real data.
- **Field:** a protocol anyone can run: the same route at each spacing, on more than one phone, with the same steps and a results sheet. EAFIT points can be tested by hand as well.
- Measures how long the user goes without hearing anything, how quickly leaving the path is noticed, and correction error.
- Ends with a recommended spacing, used by C5.
- Also compares **photo match coverage**: does spacing explain stretches with no matches, or is it the photos themselves?
- Uses the four stretches around the library as the standard route, since it has history to compare against.

**Components:** replay tooling, backend-positioning scripts, docs.

**Done when:** there's a written recommendation with its numbers, and the protocol has been run at least once.

**Tested by:** unit tests for the thinning tool; the protocol's results.

**Depends on:** B3 helps.

**Needs you:** walking the field protocol with more than one phone; a person is needed for real walking.

**From notes:** N17, N18, N19, N20, N38, N39, N40.

### B2 · Device matrix (#178)

**Problem.** The app has to work on any phone, but today's phones differ: one had no barometer, another a compass about 85° off, and logs don't say which phone a trip was on.

**Scope.**
- Log the phone model, app version, available sensors and GPS quality with each trip.
- Test the main flows across a range of phones, including low-end ones.
- Define and test what happens with each missing or bad sensor: compass, gyroscope, barometer.
- Show the results as a table of what works where.
- Android versions, including Android 10, and screen readers other than TalkBack, such as Jieshuo, which participants use.
- Time to capture a photo per phone: 1.47 s p50 on the phone in today's logs.

**Components:** application, backend-navigation-management, docs.

**Done when:** each trip says what phone it ran on, and the matrix exists for the phones we can get.

**Tested by:** unit tests for sensor fallbacks; real phones for the matrix.

**Depends on:** nothing.

**Needs you:** lending or finding the phones.

**From notes:** N22, N23, N40.

### B3 · Tools for the AI to analyze tests (#179)

**Problem.** Finding out why a trip failed took long, hand-written queries each time. Better tools make each test more useful.

**Scope.**
- One command giving a trip report: stops reached, everything said and when, stalls, pauses, heading vs compass vs movement, correction size.
- Comparison between trips and phones.
- Run logged trips through the real guidance logic offline, to check a fix against past failures before it reaches anyone.
- List what the logs are missing, and add it.
- **Photo match coverage per stretch:** which ones never match, and why (no candidates, low score, too far, heading mismatch).
- **A failure map per test:** which stretch, what failed, and the likely cause, so a test's problems can be pinpointed.

**Components:** scripts, application test harness, backend-navigation-management if logs need more.

**Done when:** the spinning and stuck trips of `docs/TUNING.md` §10 can be diagnosed with one command each, and replayed against a fix.

**Tested by:** those trips as fixtures.

**Depends on:** nothing.

**Needs you:** nothing.

**From notes:** N45, N46, N47, N48, N61.

### B4 · Sideways walking and leaving the path (#180)

**Problem.** People can face the right way but drift sideways, and the app reacts late. Testers said it took too long to say anything.

**Scope.**
- Detect walking off the line while facing correctly, from the movement vs the heading.
- Faster, clearer feedback when leaving the path, based on B1's spacing and GPS quality.
- Keep it from becoming the turn loop again: cue limits stay.
- Covers what the test notes describe: turns announced early or late, silence on whole straights, being sent the wrong way, and getting lost on the last stretch, where participants had to be guided by hand.

**Components:** application, backend-positioning if the filter helps.

**Done when:** logged and replayed walks show earlier feedback with no more false alarms than today.

**Tested by:** B3 replays; unit tests; a field walk.

**Depends on:** B1, B3.

**Needs you:** a field walk to confirm.

**From notes:** N39, N40, N48, N49.

### B5 · Test report and metrics (#181)

**Problem.** There's no one place saying how well it works. Positioning error is measured per walk; route success and SUS are still pending, and how often people get lost isn't tracked.

**Scope.**
- A report per campus and version: how much positions were corrected, route success, how often people got lost, time to arrive.
- The SUS questionnaire, and recording it.
- More participants for controlled tests, as needed.
- **The test process, written once:** what to check before merging, before a release and in the field, with the standard route and what to note down, so each test is comparable.
- Includes B3's failure map per test.

**Components:** scripts, backend-navigation-management if needed, docs.

**Done when:** one command makes the report, and it has been filled in from a real test round.

**Tested by:** running it on existing sessions.

**Depends on:** B3.

**Needs you:** running user tests; the SUS answers.

**From notes:** N21, N61, N62.

### B6 · Day and night (#182)

**Problem.** Photo matching was built from daytime photos. Evenings and nights may look too different, so the app needs to handle different light if it can.

**Scope.**
- Measure matching in daylight, at dusk and at night on the same routes.
- Test options: night photos per point, a different model, fine-tuning on campus images, or falling back to GPS with less photo correction at night.
- A proper accuracy check on a labelled set of live frames, which test walks already store (the old target was over 80%).

**Components:** backend-ai-training, backend-positioning, docs.

**Done when:** there's a measured answer on what works at night, and a recommendation.

**Tested by:** the benchmark script, on labelled frames.

**Depends on:** nothing.

**Needs you:** evening walks on campus.

**From notes:** N30.

## D. User view

### D1 · Voice first (#189)

**Problem.** Users said they don't much like using TalkBack. The simplest app is one where the first thing you do is say where you want to go.

**Scope.**
- After signing in, the app speaks and listens for the destination straight away, without TalkBack.
- A clear way to speak again, and to confirm or change.
- Buttons to choose the place by hand stay, and come back where they were removed.
- Simpler instructions on this screen.
- **Say "start":** after choosing, saying a confirmation starts the route. Participants expected this and couldn't find the button.
- **Always clear when it's listening,** with sound or vibration that the recognizer won't hear as speech.
- **A tap must not restart the flow,** which is how people got lost. No message that sounds like a button.
- The first time: microphone permission, a noisy place, and what happens when voice isn't available, or it isn't understood after a few tries.
- **Sign-in and sign-up can stay as they are:** they don't need to be simple. Voice first starts after them, and the session stays signed in.

**Components:** application.

**Done when:** someone who has never seen the app can start a trip by voice alone, with TalkBack off and on.

**Tested by:** widget tests; a test with users.

**Depends on:** nothing.

**Needs you:** a test with users.

**From notes:** N33, N34, N35.

### D5 · Holding the phone and obstacles (#200)

**Problem.** The app asks to hold the phone in front, with the camera forward. But people bring it to the ear to hear it, which points the camera away, and one participant didn't like having to depend on the phone in hand. Testers also pointed out the risk of obstacles nobody has mapped, like bins and vending machines, which the app can't warn about.

**Scope.**
- Test ways of carrying and hearing it: an earphone, a lanyard or chest mount, and how the app behaves when the camera isn't facing forward.
- Tell people the best way, in the tutorial and in the guide, once tested.
- Study whether the camera could warn of obstacles on a phone or server, how fast, and how reliably. Admin warnings on connections already exist, but only cover what's written down.
- A clear recommendation on what to build; building detection is a separate story if it's worth it.

**Components:** application, backend-ai-training for the study, docs.

**Done when:** there's a tested recommendation for carrying the phone, and a measured answer on obstacle detection.

**Tested by:** walks with each way of carrying it, comparing photo matches and hearing.

**Depends on:** B3.

**Needs you:** walking tests, and buying or borrowing a mount if it's worth trying.

**From notes:** test feedback (see D3).

## E. Speed and platform

### E1 · Supabase optimization (#193)

**Problem.** Lists and route-finding read whole tables, and the log table only grows. Indexes have never been checked against real use.

**Scope.**
- A SQL script to run in Supabase: unused and missing indexes, slow queries via `pg_stat_statements`, table sizes.
- From its results, a second script with only the indexes that help.
- A plan for trip logs as they grow.
- **The first script only reads,** and changes nothing. `pg_stat_statements` may need enabling first, which the script will explain.

**Components:** db_schema, backend services.

### E4 · Language and runtime study (#196)

## Admin parity list

Everything admins can do today, from the admin guide. After the overhaul each must still be possible, though not necessarily in the same place.

**Overall:** sign in · sign up · open the guide · help for the current page · refresh · settings (detail level, high contrast, language, text size, voice guidance) · log out · narrow-window menu.

**Menu notices:** verified points with no connections (open filtered list) · named points users can't choose (open, change type) · connections over the limit (delete) · floor changes with no stairs (delete).

**Universities:** search · list with building count · open a university's buildings, with a chip to clear that filter · add (code, name, address, latitude, longitude, pick on map) · edit · change active state · delete with what else goes with it.

**Buildings:** search · list with university and point count · open a building's points, with a chip to clear that filter · add (university, code, name, address, latitude, longitude, pick on map, floors, elevator, stairs) · edit, including moving to another university · change active state · delete with what else goes with it.

**Anchor points:**
- Find: search · filter by status with counts · filter by category and type, floor, indoors or outdoors, lighting, photos, connections · clear filters · list and map views.
- Create: university, building, floor, location type (search and categories), description, indoors or outdoors, lighting, surface · pick on map, seeing existing points · use GPS location on a phone · warning for a point under 3 m away · warning for a name on an in-between type · form remembers the last point.
- Edit: all of the above · status (pending, verified, rejected) · move on map · thumbnails.
- Photos: upload on the web with a direction · take with the camera on a phone, with heading · delete · done.
- Verify: from the list, map or edit page · refused with no photos · warning with no connections · unverify.
- From the map: see point data, connect, move (pin, save, cancel), verify, add photo, edit.
- Delete a point with what else goes with it.

**Floors:** up and down · adjacent floors shown differently · only this floor, remembered.

**Connections:** search · list with distance and warning · add on the map by tapping (chain, deselect, across floors) · add by form (university, building filter, A, B, distance, warning) · refused when over the limit or changing floor wrongly · warning over 15 m · edit a warning · delete from the list or map line · jump from a point's row, with it selected.

**Users:** list · promote and demote · activate and deactivate · repair accounts with no profile · not on your own row.

**Sessions:** by user with counts · a user's sessions · watch one on the map (route, raw GPS, corrected position, photo matches, wrong-instruction marks, summary card, legend, tap for details, follow live) · view its comment · delete · refresh · floor buttons for multi-floor routes.

**Feedback:** read comments with who, when and how the trip ended.

**Re-index:** run it · see "N photos not searchable" · see what failed.

**Phone only:** take photos with the camera · Test as user (wrong-instruction button, checkpoints, start-point check).
