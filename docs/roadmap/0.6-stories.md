# 0.6 stories

Everything planned for the 0.6 release. Stories are medium-sized: each takes one to four components that can reasonably be done together. They have no dates; the groups are in the order to start them. Each one is also a GitHub issue in the `0.6` milestone.

**How to read a story's "From notes":** the numbers point to the [coverage table](#coverage-every-request-mapped-to-a-story), which lists every request made for this release and the story that takes it.

## A. Event readiness

The event needs 10 to 30 people navigating at once, on the AWS Academy lab. Server-side work here needs no app release, so it can go live on its own.

### A1 · Load test and baseline (#173)

**Problem.** Nobody knows how many people the app can serve. The only figures are from one user at a time, and the 8-person limit above is an estimate.

**Scope.**
- A tool that simulates N people on a trip: real photos and GPS through `POST /correct_position`, plus the trip's logs and route calls, at the pace a phone sends them.
- Runs at 10, 20 and 30 people, reporting p50, p95 and errors per endpoint, and the point where it stops keeping up.
- Reports CPU and memory on the server, and CPU credit use, since t3 machines slow down when credits run out.
- Saved results, to compare every later change against.

**Components:** load test tool, backend-positioning, backend-ai-training.

**Done when:** one command gives the numbers above against the deployed server, and the baseline is written down.

**Tested by:** running it. It uses a test account and throwaway session ids, and doesn't run while people are testing.

**Depends on:** nothing.

**From notes:** N24, N25, N42, N44, N57.

### A2 · Position correction under load (#174)

**Problem.** Photo search is slow, and when requests pile up every user waits. An overloaded correction shouldn't stop guidance, because guidance already works from GPS alone.

**Scope.**
- Limit how many photo searches run at once in backend-ai-training.
- When busy, backend-positioning answers quickly with the GPS-based result instead of queuing, and says so in the response.
- The app sends fewer photos when told the server is busy, and goes back to normal after.
- Review the gateway's per-user and per-address limits for a whole event on one Wi-Fi address.

**Components:** backend-ai-training, backend-positioning, application, gateway.

**Done when:** at 30 simulated people, responses stay under an agreed p95 and no one gets errors, even if some get fewer photo corrections.

**Tested by:** A1 before and after; unit tests of the busy behavior; older app versions keep working, since the response only gains a field.

**Depends on:** A1.

**From notes:** N42, N43, N44.

### A3 · Load balancing on what Academy allows (#175)

**Problem.** One small machine runs everything. A2 protects users, but serving more people needs more CPU.

**Scope.**
- Check which machine sizes and how many machines the Academy lab allows.
- Use the result: a bigger machine, and/or a second one only for photo search, with the gateway balancing between them.
- Compose and deploy changes to match, with secrets staying off the repo.

**Components:** deployment, docker-compose, gateway.

**Done when:** A1 shows the target is met, or we know exactly what limits it and what the fallback is.

**Tested by:** A1 against the new setup; a test of one search machine failing during load.

**Depends on:** A1, A2 helps.

**From notes:** N24, N31, N32, N43, N44.

### A4 · Event runbook and rehearsal (#176)

**Problem.** A live event can't depend on someone remembering how to keep the lab alive.

**Scope.**
- Runbook: starting the lab, refreshing credentials, deploying, what to watch, and what to do when something fails.
- A simple live view of request rate, latency, errors and CPU.
- A full rehearsal with A1, on the real setup.
- A go/no-go list deciding which 0.6 work is live for the event. Anything not ready waits.
- Phones updated, and a demo plan including the case where the server is overloaded.

**Components:** deployment, docs.

**Done when:** the rehearsal has passed, and someone other than the author can follow the runbook.

**Tested by:** the rehearsal itself, including one deliberate failure.

**Depends on:** A1, A2, A3.

**From notes:** N42, N43.

## B. Measure what fails

### B1 · Anchor point spacing experiment (#177)

**Problem.** The main suspect for the poor Icesi results is points placed too far apart, compared with the closer spacing that worked at EAFIT. It needs measuring, so the limits come from evidence.

**Scope.**
- **Offline:** thin EAFIT's route to about 4–5 m, 8 m and 12–15 m and replay logged walks (`backend-positioning/scripts/replay.py`) on copies, never changing real data.
- **Field:** a protocol anyone can run: the same route at each spacing, on more than one phone, with the same steps and a results sheet. EAFIT points can be tested by hand as well.
- Measures how long the user goes without hearing anything, how quickly leaving the path is noticed, and correction error.
- Ends with a recommended spacing, used by C5.

**Components:** replay tooling, backend-positioning scripts, docs.

**Done when:** there's a written recommendation with its numbers, and the protocol has been run at least once.

**Tested by:** unit tests for the thinning tool; the protocol's results.

**Depends on:** B3 helps.

**From notes:** N17, N18, N19, N20, N38, N39, N40.

### B2 · Device matrix (#178)

**Problem.** The app has to work on any phone, but today's phones differ: one had no barometer, another a compass about 85° off, and logs don't say which phone a trip was on.

**Scope.**
- Log the phone model, app version, available sensors and GPS quality with each trip.
- Test the main flows across a range of phones, including low-end ones.
- Define and test what happens with each missing or bad sensor: compass, gyroscope, barometer.
- Show the results as a table of what works where.

**Components:** application, backend-navigation-management, docs.

**Done when:** each trip says what phone it ran on, and the matrix exists for the phones we can get.

**Tested by:** unit tests for sensor fallbacks; real phones for the matrix.

**Depends on:** nothing.

**From notes:** N22, N23, N40.

### B3 · Tools for the AI to analyze tests (#179)

**Problem.** Finding out why a trip failed took long, hand-written queries each time. Better tools make each test more useful.

**Scope.**
- One command giving a trip report: stops reached, everything said and when, stalls, pauses, heading vs compass vs movement, correction size.
- Comparison between trips and phones.
- Run logged trips through the real guidance logic offline, to check a fix against past failures before it reaches anyone.
- List what the logs are missing, and add it.

**Components:** scripts, application test harness, backend-navigation-management if logs need more.

**Done when:** the spinning and stuck trips of `docs/TUNING.md` §10 can be diagnosed with one command each, and replayed against a fix.

**Tested by:** those trips as fixtures.

**Depends on:** nothing.

**From notes:** N45, N46, N47, N48.

### B4 · Sideways walking and leaving the path (#180)

**Problem.** People can face the right way but drift sideways, and the app reacts late. Testers said it took too long to say anything.

**Scope.**
- Detect walking off the line while facing correctly, from the movement vs the heading.
- Faster, clearer feedback when leaving the path, based on B1's spacing and GPS quality.
- Keep it from becoming the turn loop again: cue limits stay.

**Components:** application, backend-positioning if the filter helps.

**Done when:** logged and replayed walks show earlier feedback with no more false alarms than today.

**Tested by:** B3 replays; unit tests; a field walk.

**Depends on:** B1, B3.

**From notes:** N39, N40, N48, N49.

### B5 · Test report and metrics (#181)

**Problem.** There's no one place saying how well it works. Positioning error is measured per walk; route success and SUS are still pending, and how often people get lost isn't tracked.

**Scope.**
- A report per campus and version: how much positions were corrected, route success, how often people got lost, time to arrive.
- The SUS questionnaire, and recording it.
- More participants for controlled tests, as needed.

**Components:** scripts, backend-navigation-management if needed, docs.

**Done when:** one command makes the report, and it has been filled in from a real test round.

**Tested by:** running it on existing sessions.

**Depends on:** B3.

**From notes:** N21.

### B6 · Day and night (#182)

**Problem.** Photo matching was built from daytime photos. Evenings and nights may look too different, so the app needs to handle different light if it can.

**Scope.**
- Measure matching in daylight, at dusk and at night on the same routes.
- Test options: night photos per point, a different model, fine-tuning on campus images, or falling back to GPS with less photo correction at night.
- A proper accuracy check on a labelled set of live frames, which test walks already store (the old target was over 80%).

**Components:** backend-ai-training, backend-positioning, docs.

**Done when:** there's a measured answer on what works at night, and a recommendation.

**Tested by:** the benchmark script, on labelled frames.

**Depends on:** nothing.

**From notes:** N30.

## C. Admin overhaul

The rule for this whole group: **admins can do everything they can today.** The [parity list](#admin-parity-list) is the check.

### C1 · Parity list and one shared map (#183)

**Problem.** Each admin page has its own way of showing the map, and data lives in separate lists. Overhauling that safely starts with knowing what must not be lost.

**Scope.**
- Turn the parity list into tests or a checked list, used by C2 to C4.
- One map component with layers (campus, building, point, connection), replacing the shared logic of today's map screens.
- A short design of the new flow, agreed before building the rest.

**Components:** application, tests.

**Done when:** an existing map screen runs on the shared component with no lost function.

**Tested by:** widget tests; `docs/admin-guide/tools` screenshots to compare.

**Depends on:** nothing.

**From notes:** N1, N2, N3, N14, N15.

**Problem.** Finding anything means jumping between lists. The map should be the first thing, with the data directly on it.

**Scope.**

- Search in every view jumps the camera to a university, building or point.
- Click a university: its buildings appear. Click a building: its points appear.
- Hovering shows the data, and details open from the map.
- Works at phone width, without hover.

**Components:** application.

**Done when:** an admin can get from the top to any point and its data without leaving the map.

**Tested by:** widget tests; the parity list; a real admin trying it.

**Depends on:** C1.

**From notes:** N3, N4, N5, N6, N7, N8, N9, N10.

**Components:** application, backend-map-management if the map needs lighter queries.

### C4 · Visual system and colors (#186)

**Problem.** Colors aren't coherent across screens, and what they mean isn't clear. Floors use purple and orange beside green status colors, which may be hard to read.

**Scope.**
- Research which colors work best for what's being looked at; floors in red and blue is the first option to test.
- One palette in one place, for status, floors and connections, for all screens.
- Keep shape as well as color, and check contrast and colorblindness, on the map background.

**Components:** application, screenshot tooling.

**Done when:** all admin screens use the palette, with the reasons written down.

**Tested by:** contrast checks; widget tests; retaken screenshots.

**Depends on:** C1.

**From notes:** N1, N12, N13.

**Problem.** The limits (30 m maximum, a warning at 15 m) allowed points far apart, and fixing a map afterwards is manual.

**Scope.**

- List and highlight stretches that need more points, and make adding a point in between easy.

**Components:** application, backend-map-management, backend-route-management.

**Done when:** an admin can see and fix Icesi's wide stretches from the map, and new ones are refused or warned about.

**From notes:** N16, N17, N18, N19.

## E. Speed and platform

### E1 · Supabase optimization (#193)

**Problem.** Lists and route-finding read whole tables, and the log table only grows. Indexes have never been checked against real use.

**Scope.**
- A SQL script to run in Supabase: unused and missing indexes, slow queries via `pg_stat_statements`, table sizes.
- From its results, a second script with only the indexes that help.
- A plan for trip logs as they grow.

**Components:** db_schema, backend services.

**Done when:** you've run the scripts, and the slowest queries have measured before and after figures.

**Tested by:** `EXPLAIN ANALYZE` on the real queries.

**Depends on:** nothing.

**From notes:** N52.

### E2 · API and frontend speed (#194)

**Problem.** Screens wait longer than they should, and nobody has measured where. For example, `/anchor-points` sends every point to every screen.

**Scope.**
- Measure what users wait for: app startup, destinations, finding a route, admin screens, and what the frontend itself costs.
- Fix the worst: lighter endpoints that stay additive, caching where measured, and smaller photo work (input size, int8/ONNX, closer Qdrant).
- Revisit the 500 ms target with today's numbers.

**Components:** backend services, application.

**Done when:** the main actions have a measured p95 and the slowest are improved.

**Tested by:** A1; new timings; existing test suites.

**Depends on:** A1.

**From notes:** N25, N26, N27, N51, N57.

### E3 · Behavior test suite (#195)

**Problem.** Any big change, such as a rewrite, needs proof that everything still works the same. Tests today are per service.

**Scope.**
- End-to-end tests over the gateway for the real flows: sign-in, capture, connect, route, trip, logs.
- Contract tests of every endpoint the app uses, including older app versions.
- Runs in CI, against any implementation of a service.

**Components:** all backend services, gateway, CI.

**Done when:** the suite runs in CI, and a deliberately broken endpoint fails it.

**Tested by:** itself.

**Depends on:** nothing.

**From notes:** N50, N56.

### E4 · Language and runtime study (#196)

**Problem.** Are other languages or runtimes worth it? This is one big story because splitting it would be harder to check, and any change in it is breaking.

**Scope.**
- Benchmark Rust, Go, and JavaScript where it fits (Bun vs Node), against today's Python, on the real hot paths: gateway-level calls, route-finding, positioning's filter, list endpoints.
- Compare p95, throughput, memory, reliability and how hard it is to maintain.
- A recommendation. **Note:** photo search time is mostly the model, so a language change may gain little there. Any rewrite is decided after this, with E3 proving the same behavior.

**Components:** benchmarks, one prototype service per candidate, docs.

**Done when:** a written recommendation with its numbers.

**Tested by:** A1's tool, and E3 against any prototype.

**Depends on:** A1, E3.

**From notes:** N50, N51, N55, N56, N57.

### E5 · Queue evaluation (#197)

**Problem.** Would Kafka or RabbitMQ help? The likely candidate is writing trip logs in the background, so a trip's calls don't wait on them.

**Scope.**
- Measure what waits today, and test a queue on that path.
- Compare Kafka, RabbitMQ and simpler options (a background task, a database queue), including the cost of running them.
- It may honestly conclude "not needed at this size".

**Components:** backend-navigation-management, backend-positioning, docs.

**Done when:** a written decision with its numbers.

**Tested by:** A1 with and without it.

**Depends on:** A1.

**From notes:** N53.

### E6 · Deployment improvements (#198)

**Problem.** Deploying is manual, one machine does everything, and the account can stop it.

**Scope.**
- Repeatable deploys with rollback, and health checks.
- Better use of a second machine and of AWS resources.
- Production plan for moving off Academy, with monitoring and cost limits (with #93).

**Components:** deployment, CI, docker-compose.

**Done when:** a deploy and a rollback are each one command, and the production plan is written.

**Tested by:** a rollback on the real server.

**Depends on:** A3 and A4's lessons.

**From notes:** N31, N32.

## Admin parity list

Everything admins can do today, from the admin guide. After the overhaul each must still be possible, though not necessarily in the same place.

**Overall:** sign in · sign up · open the guide · help for the current page · refresh · settings (detail level, high contrast, language, text size, voice guidance) · log out · narrow-window menu.

**Menu notices:** verified points with no connections (open filtered list) · named points users can't choose (open, change type) · connections over the limit (delete) · floor changes with no stairs (delete).

**Universities:** search · list with building count · add (code, name, address, latitude, longitude, pick on map) · edit · change active state · delete with what else goes with it.

**Buildings:** search · list with university and point count · add (university, code, name, address, latitude, longitude, pick on map, floors, elevator, stairs) · edit, including moving to another university · change active state · delete with what else goes with it.

**Anchor points:**
- Find: search · filter by status with counts · filter by category and type, floor, indoors or outdoors, lighting, photos, connections · clear filters · list and map views.
- Create: university, building, floor, location type (search and categories), description, indoors or outdoors, lighting, surface · pick on map, seeing existing points · use GPS location on a phone · warning for a point under 3 m away · warning for a name on an in-between type · form remembers the last point.
- Edit: all of the above · status (pending, verified, rejected) · move on map · thumbnails.
- Photos: upload on the web with a direction · take with the camera on a phone, with heading · delete · done.
- Verify: from the list, map or edit page · refused with no photos · warning with no connections · unverify.
- From the map: see point data, connect, move (pin, save, cancel), verify, add photo, edit.
- Delete a point with what else goes with it.

**Floors:** up and down · adjacent floors shown differently · only this floor, remembered.

**Connections:** search · list with distance and warning · add on the map by tapping (chain, deselect, across floors) · add by form (university, building filter, A, B, distance, warning) · refused when over the limit or changing floor wrongly · warning over 15 m · edit a warning · delete from the list or map line · jump from a point's row, with it selected.

**Users:** list · promote and demote · activate and deactivate · repair accounts with no profile · not on your own row.

**Sessions:** by user with counts · a user's sessions · watch one on the map (route, raw GPS, corrected position, photo matches, wrong-instruction marks, summary card, legend, tap for details, follow live) · view its comment · delete · refresh · floor buttons for multi-floor routes.
