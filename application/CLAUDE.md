## What this app does

Single Flutter codebase serving two roles from the root README's design: `user` (picks a trip, navigates it, receives a corrected position) and `admin` (captures anchor points/their photos, builds the walkability graph, watches active sessions live). `lib/main.dart` loads `.env` (`flutter_dotenv`), initializes Supabase Auth, and shows `AuthGate` — real login/signup and role branching. `UserHomeScreen` (`lib/user/`) *is* the trip-planning flow now, not a map and not a screen reached via a FAB: the user only picks a destination (`anchor_point_picker_screen.dart`'s Place → Building → anchor-point drill-down) - the start point is auto-selected as the verified anchor point nearest their current GPS fix (`lib/services/geo_utils.dart`'s `haversineMeters`, Uber-pickup-pin style), not picked by hand. There is no flat pre-made route list either; a route is found or computed on the fly between the auto-selected start and the picked destination (`backend-route-management`'s `POST /routes/find_or_create`, real pathfinding over the `anchor_point_connections` graph). The admin side has the original two-step capture flow — `lib/admin/capture_screen.dart` (creates the `anchor_points` row: place/building/type/description/position) then `lib/admin/capture_photo_screen.dart` (the ~4-8-photos-per-point loop) — plus place/building/anchor-point creation/editing, the connections-graph builder, and now `live_sessions_screen.dart`/`session_tracking_screen.dart` for watching an active user's navigation session (full logged trail, not just the latest point) on a map in real time.

## How it connects to the rest of the system

`lib/services/api_service.dart` gives the app real HTTP clients for every backend service — `UserManagementApi`, `MapManagementApi`, `RouteManagementApi`, `NavigationManagementApi`, `DataCollectionApi` — each built from a single `API_GATEWAY_URL` in `.env` plus its own fixed path prefix (`/user`, `/map`, `/route`, `/navigation`, `/data-collection`), routed by the API gateway (`gateway/nginx.conf`) to the matching backend service. This is a change from before — previously the app read 5 separate base-URL env vars, and `backend-data-collection` wasn't wired through this pattern at all (see Known gaps history).

- **Auth**: `lib/auth/signup_screen.dart` calls Supabase Auth's `signUp`, then `UserManagementApi().post('/profiles', ...)` with the new auth user's id and `role_id: 1` (`user`) — the real trigger for `backend-user-management`'s `POST /profiles` that every service's `CLAUDE.md` previously described as "nothing calls this." `login_screen.dart` calls `signInWithPassword`. Both rely on `AuthGate`'s `Supabase.instance.client.auth.onAuthStateChange` listener to react to the resulting session change, rather than navigating manually.
- **Role routing**: `AuthGate` fetches `GET /profiles/{id}` (`backend-user-management`) for the signed-in user and shows `AdminHomeScreen` if `role_id == 2`, else `UserHomeScreen` — matching `db_schema/roles.sql`'s seeded `user`/`admin` ids (hardcoded as `kUserRoleId`/`kAdminRoleId` rather than fetched, since `roles` has no reason to change at runtime).
- **Photo upload**: `SimpleCameraWidget._sendPhotoToServer` now calls `DataCollectionApi().postMultipart('/upload', ...)` (fixed alongside the API gateway work — it used to hardcode a URL rather than reading any config); the multipart field name matches `backend-data-collection`'s parameter (`image`) since that service's `POST /upload` signature was fixed. It also captures a live `flutter_compass` heading (same subscribe-in-`initState`/cancel-in-`dispose`/freeze-at-capture pattern as `capture_photo_screen.dart`'s anchor-point photos) and sends it as an optional `heading` form field, omitted entirely rather than sent as null when no compass reading is available yet.
- **Anchor-point creation and photos**: `lib/admin/capture_screen.dart` only creates the `anchor_points` row (`POST /anchor-points` — `building_id`, `location_type_id`, `latitude`/`longitude`/`altitude`, and a now-required `location_description`, since it doubles as the point's display name) and, on success, pushes `lib/admin/capture_photo_screen.dart` with the new id. That screen is the real client for `POST /anchor-points/upload-image` (via `MapManagementApi.postMultipart`) and `POST /anchor-points/{id}/photos` — each photo carries its own `heading` (live compass reading, frozen at capture time) and `captured_by` (the signed-in admin's id), since one physical point typically gets ~4-8 photos facing different directions (see `backend-map-management/CLAUDE.md`'s anchor-points/photos schema split). It shows a thumbnail grid of photos taken so far (existing ones fetched via `GET /anchor-points/{id}/photos`, so it also works for adding photos to an already-captured point), each deletable (`DELETE /anchor-point-photos/{id}`). `admin_home_screen.dart` fetches `GET /places`, `GET /buildings`, `GET /anchor-points`, `GET /anchor-point-photos`, and `GET /anchor-point-connections` together for its four tabs (see below).
- **Admin home tabs, search, edit, delete**: `admin_home_screen.dart` is a 4-section screen — Places / Buildings / Anchor points / Connections — navigated via a side `Drawer` (hamburger icon, auto-added by `Scaffold` once a `drawer:` is set) rather than a top `TabBar`; the AppBar title reflects whichever section is active. Internally it's still a `TabController`/`TabBarView` (swipe disabled via `NeverScrollableScrollPhysics` now that the tab indicator isn't visible) — the drawer's `ListTile`s just call `_tabController.animateTo(index)` and close themselves, so `_fab()`'s per-section switch, the Connections-only "Add connection" AppBar action, and the drill-down `animateTo()` calls described below all keep working unchanged. Each section has a client-side search field (by name for places/buildings, by either endpoint's description for anchor points/connections) and a per-row Edit action into `edit_place_screen.dart`/`edit_building_screen.dart`/`edit_anchor_point_screen.dart` (`PATCH` counterparts of the `Add*Screen`s, pre-filled — connections have no edit, delete-and-recreate instead). Anchor-point rows also show a thumbnail (first photo, if any), a photo count, and an "Add photo" action straight into `capture_photo_screen.dart`. Delete (`DELETE /places/{id}`, `/buildings/{id}`, `/anchor-points/{id}`, `/anchor-point-connections/{id}`) is behind a confirmation dialog that states the real cascade impact — counts of buildings/anchor points/photos/connections that will also be deleted — computed client-side from the five already-loaded lists, since `places`→`buildings`→`anchor_points`→(`anchor_point_photos`, `anchor_point_connections`) are all `ON DELETE CASCADE`. The floating action button swaps per active tab (Add place / Add building / New anchor point / Connect on map); the Connections tab also gets a secondary app-bar action ("Add connection (form)") into `add_connection_screen.dart`. A `RefreshIndicator` and an app-bar refresh button reload all five lists. The Anchor points tab also has a status filter (`ChoiceChip`s: All/Pending/Verified/Rejected, each showing a count) above the search field — this is the "pending-review queue," composing with the existing description search rather than replacing it. Tapping a place row (not its Edit/Delete icons) drills down: it sets `_buildingsPlaceFilterId` and switches to the Buildings tab, which then layers a `place_id` filter on top of (not instead of) its own text search, shown as a clearable `InputChip` ("Buildings in <place>") — the same `place_id`/`building_id` scoping `LocationPickerScreen`'s `buildingsPlaceId`/`anchorPointsBuildingId` params already use elsewhere, just applied to this screen's own tabs. Tapping a building row does the same one level down: sets `_anchorPointsBuildingFilterId` and switches to the Anchor points tab, layering a `building_id` filter on top of (not instead of) its existing status chips and description search, shown as its own clearable `InputChip` ("Anchor points in <building>"). `_loadData()` clears either stale scope if the scoped place/building no longer exists after a refresh.
- **Anchor-point verification**: `edit_anchor_point_screen.dart` now shows a read-only horizontal thumbnail strip of the point's photos (fetched via `GET /anchor-points/{id}/photos`, same call `capture_photo_screen.dart` makes) plus a "Manage photos" button into `CapturePhotoScreen` — an admin reviewing whether to set `status` to `verified`/`rejected` has something to actually look at instead of judging from lat/lng/description alone. `LocationPickerScreen`'s anchor-point markers are now color-coded by `status` (green/grey/red for verified/pending/rejected) instead of a flat green dot, so verified points are visually distinct on every screen that overlay appears on (`CaptureScreen`, `AddBuildingScreen`/`EditBuildingScreen`, `EditAnchorPointScreen`'s own "Move on map"). `connect_anchor_points_screen.dart` has its own separate marker rendering for building the connections graph and isn't part of this.
- **Qdrant indexing on verify**: `lib/services/api_service.dart`'s `AiTrainingApi` (prefix `/ai-training`) is the real client for `backend-ai-training`'s `POST /index_anchor` — right after `edit_anchor_point_screen.dart`'s `PATCH` succeeds with `status: 'verified'`, it posts the anchor point's id/position/building plus its already-loaded `_photos` (id/image_url/heading, no extra fetch) so only confirmed-good anchor points enter the Qdrant-searchable index. If indexing fails, the screen stays open with an inline error instead of popping (the verify itself already saved) — re-tapping Save safely retries, since indexing upserts by photo id are idempotent. Saving an already-verified point (e.g. just to move it) re-indexes all its current photos too, refreshing the stored coordinates. Saving with any **other** status (moving a point back to `pending`, or to `rejected`) instead calls `DELETE /index_anchor/{id}` — best-effort, doesn't block saving — so a downgraded point actually leaves the searchable index instead of just no longer being re-indexed.
- **Keeping Qdrant in sync afterward**: `capture_photo_screen.dart` fetches the anchor point's own record (`GET /anchor-points/{id}`) alongside its photos so it knows whether the point is already verified — adding a photo there indexes just that one new photo when it is (`POST /index_anchor` with a single-item `photos` list), and deleting a photo there always calls `DELETE /index_photo/{id}` on `backend-ai-training` (harmless no-op if it was never indexed). `admin_home_screen.dart`'s three cascade-delete handlers (place/building/anchor point) each call a matching Qdrant cleanup endpoint (`DELETE /index_anchor/{id}` or `/index_building/{id}`, looped over every affected building for a place) before the Postgres delete — wrapped in a `_bestEffort` helper that swallows `ApiException` internally, since a stray Qdrant failure shouldn't block a delete the admin already confirmed.
- **Anchor-point connections (walkability graph)**: `connect_anchor_points_screen.dart` is the primary way to build the graph — a place/building-filtered `flutter_map` showing every anchor point as a tappable marker (existing connections between visible points drawn as green `Polyline`s), where tapping one point then another calls `POST /anchor-point-connections` (`created_by` = signed-in admin id, `distance_meters` omitted so the backend computes straight-line distance) and leaves the just-tapped point selected so a corridor can be chain-connected point by point without re-entering the flow. `add_connection_screen.dart` is the dropdown-based fallback (place → optional building filter → anchor point A/B dropdowns → optional distance override/notes) for when precision matters more than speed, or the admin isn't near a map. Neither screen pre-checks for an existing connection before posting — a duplicate (in either id order) is caught by the backend's `UNIQUE` constraint and surfaces as a generic "already connected" snackbar message, not a hard block.
- **Place/building creation**: `admin_home_screen.dart`'s per-tab FAB opens `lib/admin/add_place_screen.dart` (`POST /places`) and `lib/admin/add_building_screen.dart` (`POST /buildings`, with a place dropdown from `GET /places`) — closes the gap where `places`/`buildings` had to be seeded by hand in Supabase before an admin could capture any anchor point.
- **Map-pin location picking**: `lib/admin/location_picker_screen.dart` is a reusable `flutter_map` screen (same tile setup as `map.dart`) that pops a tapped `LatLng` back to its caller — used by `add_place_screen.dart`/`edit_place_screen.dart`, `add_building_screen.dart`/`edit_building_screen.dart`, `capture_screen.dart` (a nullable `_pickedPosition` that takes priority over `LocationService().lastPosition` at submit time, and relaxes the old "GPS required" guard to accept either a GPS fix or a manual pick), and `edit_anchor_point_screen.dart` ("Move on map"). This closes the map-pin-picker half of what was tracked as GitHub issue #37. Its app-bar "Confirm" action is an `IconButton` (a checkmark), not a `TextButton` with a hardcoded text color — an earlier version used white text on a light AppBar and was effectively invisible.
- **Existing-data overlay on the picker**: `LocationPickerScreen` optionally fetches and overlays existing places (`Icons.flag`, purple, badged with their building count)/buildings (`Icons.apartment`, orange, badged with their anchor-point count)/anchor points (plain green dot — heading now lives per-photo, not on the anchor point itself, so it's no longer meaningful to show on this overlay) via `showPlaces`/`showBuildings`/`showAnchorPoints` flags, self-fetching via its own `MapManagementApi()` rather than requiring callers to pre-fetch. `buildingsPlaceId`/`anchorPointsBuildingId` scope the buildings/anchor-points overlays to one place/building (`CaptureScreen`/`AddBuildingScreen`/`EditBuildingScreen` pass these so the map only shows what's actually relevant to the form being filled in, not every building or anchor point in the system). Lets an admin see duplicates/coverage gaps while picking a new location.
- **Anchor-point-photo heading**: `capture_photo_screen.dart` captures a real compass heading (`flutter_compass`, magnetometer-based — `geolocator`'s `Position.heading` is GPS course-over-ground and meaningless while standing still to photograph a fixed point) via `FlutterCompass.events`, shown live over the camera preview ("Facing: N°") and frozen at the moment each photo is taken (not at submit time, since the admin could reorient between photos). Sent as `heading` in the `POST /anchor-points/{id}/photos` payload. No Android manifest changes needed (location permissions flutter_compass also wants are already declared for `geolocator`); no `ios/` directory exists in this project.
- **Tile source**: `lib/services/map_tile_config.dart` holds the one `TileLayer` URL/user-agent both `map.dart` and `location_picker_screen.dart` use — the official `tile.openstreetmap.org`, not the OpenStreetMap France "hot" mirror this used to point at, which started rejecting requests from the app under its own usage policy (served a "does not respect ... base map usage policy" placeholder image instead of real tiles). Note OSM.org's own tile server also discourages heavy/production use — fine for now, but a real deployment should eventually move to a committed provider with an API key (MapTiler, Stadia Maps, etc.).
- **Trip planning**: `lib/user/user_home_screen.dart` ("Where to?") is the real client for `backend-route-management`'s `POST /routes/find_or_create` — the Uber-style replacement for both a flat pre-made route list (`route_list_screen.dart`, removed) and an earlier version of this screen that made the user pick both a start and an end point (`plan_trip_screen.dart`, also removed - folded directly into `UserHomeScreen` once the start point became auto-selected, since there was no longer a second screen's worth of UI left to justify). It pushes `anchor_point_picker_screen.dart` once, for the destination only - a Place → Building → anchor-point drill-down (three sequential list steps inside one `StatefulWidget`, not three separate pushed screens, so going "back" from the anchor-point step returns to the building step rather than exiting the whole picker; anchor points are filtered to `status == 'verified'`, since an unverified point has no indexed photos and isn't a trustworthy destination for the correction pipeline). The start point is computed client-side: fetch every verified anchor point, pick the one with the smallest `haversineMeters` distance (`lib/services/geo_utils.dart`) to `LocationService().lastPosition`. Submitting calls `find_or_create` with that computed start plus the picked end, which either returns an existing route for that exact `(start, end)` pair or computes a new one via Dijkstra over `anchor_point_connections` (see `backend-route-management/CLAUDE.md`) - a 404 ("no walkable path") is shown inline rather than silently failing, since the connections graph is hand-built by admins and may simply not cover that pair yet. On success it pushes `navigation_screen.dart` with the resulting route.
- **Navigation session lifecycle**: `navigation_screen.dart` is the real client for `backend-navigation-management`: `POST /sessions` on start (now also sending `start_position`/`device_info`, previously always omitted), `PATCH /sessions/{id}` on end, and an optional `POST /feedback` from a post-session dialog.
- **Admin live tracking**: `lib/admin/live_sessions_screen.dart` lists currently-`active` sessions (`GET /navigation/sessions`, filtered client-side - same "fetch all, filter client-side" convention as everywhere else, there's no server-side status filter param). Tapping one opens `session_tracking_screen.dart`, which polls `GET /navigation/logs` every ~4s (a repeating `Timer`, not a single fetch), filters client-side to that `session_id`, sorts by `timestamp`, and draws the **full trail** (a `Polyline` through every logged point so far, using `corrected_lat`/`corrected_long` when a tick has them else raw `gps_lat`/`gps_long`) plus a marker at the latest point - a dedicated `FlutterMap` here rather than reusing `SimpleMapWidget`, since this view has no live-GPS-stream concept, just historical data. It also fetches the session's route (`GET /route/routes/{id}` then each anchor's lat/lng via `GET /map/anchor-points/{id}`) and overlays the *planned* path in a second color, so an admin can visually compare the intended route against what was actually logged - directly useful for testing the correction pipeline, which is the scenario this screen exists for.
- **Position correction tick**: `navigation_screen.dart` also now drives `backend-positioning`'s `POST /correct_position` (via a new `PositioningApi`, prefix `/positioning`) — its first real caller. Not a `Timer.periodic`: a self-rescheduling loop (`_runTick`) fires once, then schedules the next run 1s after the *current one finishes* rather than 1s after it started, so a slow round-trip (camera shutter + CNN embedding + Qdrant search, ~600ms-1s per #122) can't cause ticks to overlap or queue up for the same session. Each tick captures a live frame via a background `CameraController` (same init pattern as `SimpleCameraWidget` in `lib/camera.dart` - `Permission.camera.request()` → `availableCameras()` → `CameraController(..., ResolutionPreset.medium)`), posts it with the current GPS fix, then forwards the response's `corrected_lat`/`corrected_long`/`correction_error`/`anchor_match_id`/`confidence_score` straight into the same `POST /logs` call alongside the raw `gps_*` fields - no reshaping needed, `backend-positioning/CLAUDE.md` documents the response as deliberately shaped for this hand-off. Any failure in this path (camera permission denied/unavailable, `/correct_position` unreachable or slow, auth rejected) degrades to the old raw-GPS-only `POST /logs` call for that tick - never blocks navigation. The camera preview itself is never shown in a release build (`kDebugMode`-gated, `package:flutter/foundation.dart`) since the primary user is visually impaired; in a debug build it appears as a small corner overlay so a developer can sanity-check what's being captured. `map.dart`'s `SimpleMapWidget` gained an `extraMarkers` param (default `[]`, additive) so this screen can show a second, green pin at the corrected position alongside the existing blue live-GPS one.
- **Settings screen (#85, #107)**: `lib/user/settings_screen.dart`, reachable from a gear icon on `UserHomeScreen`. Reads/writes `profiles.preferences` (`GET`/`PATCH /profiles/{id}`, already-existing endpoints, no backend change) for `verbosity` (low/medium/high - genuinely drives on-screen text density down the line, not implemented yet beyond the setting itself existing) and `high_contrast` (a `Switch`, defaulting to `MediaQuery.of(context).highContrast` - the OS-level signal - when never explicitly set) and `language` (`null`/`'en'`/`'es'`). Deliberately **does not** include a voice/text `feedback_type` toggle, even though that key already exists in `profiles.preferences`'s default shape from early in the project - "voice feedback" properly means the OS screen reader (TalkBack/VoiceOver) reading the screen aloud, which needs correct `Semantics`/`semanticLabel` on icon-only controls and color-only indicators (#82, not done this round) rather than an app-level preference; TalkBack is a system setting the user already controls themselves. A literal "the app speaks out loud" feature would be real TTS (#83/#39), also not done this round. Shipping the toggle with neither behind it would be a dead control.
- **High contrast / language take effect immediately, app-wide**: `lib/services/app_preferences.dart` holds two `ValueNotifier`s (`highContrastNotifier: bool`, `localeNotifier: Locale?`) that `MainApp` (`lib/main.dart`) wraps in `ValueListenableBuilder`s to pick `ThemeData` (Flutter's built-in `ColorScheme.highContrastLight()`/`highContrastDark()`, zero custom color design) and `MaterialApp.locale` (`null` = device-locale auto-detect). `AuthGate` calls `applyPreferences(...)` once, right after a successful profile fetch - deliberately *not* synchronously inside `build()`, since mutating a `ValueNotifier` an ancestor's `ValueListenableBuilder` listens to while a descendant (`AuthGate`) is still mid-build would trip a "setState called during build" assertion; doing it in the async continuation after the fetch's `await` avoids that entirely. `SettingsScreen` calls it again immediately on save.
- **Permission-denial error states (#84)**: `LocationService.initialize()` (`lib/services/location_service.dart`) already detected every failure case (service disabled, denied, permanently denied) but nothing ever read the result - `main.dart` discarded it, and `LocationInfo`/`SimpleCameraWidget` just showed an infinite spinner forever with zero explanation. `LocationService` now exposes `lastError` (a `LocationError` enum, not a raw string, so callers pick a localized message/recovery action per case rather than string-matching English text) alongside `lastPosition`. `LocationInfo` (`lib/location.dart`) and `SimpleCameraWidget` (`lib/camera.dart`) both now render a real error plus a working recovery button instead (`Geolocator.openLocationSettings()` for a disabled service, `openAppSettings()` for a permanently-denied permission, a plain retry for a merely-denied one).
- **Admin Users tab (#95)**: `AdminHomeScreen` is a 5-tab screen now (`TabController(length: 5, ...)`); the new Users tab calls `GET /profiles` (admin-only, previously had zero callers in `lib/`) and offers promote/demote (`PATCH /profiles/{id}` with `role_id: 2`/`1`) per row, with a confirmation dialog on demote and the action disabled on the signed-in admin's own row (a cheap, not-explicitly-requested safety rail against accidental self-lockout). `_fab()`'s old `default:` branch returned the Connect-on-map FAB for *any* unmatched tab index, which would have incorrectly shown it on this new tab too - changed to an explicit `case 3:` plus `case 4: return null;` (no FAB; accounts are created via signup, not an admin "add" action). Bootstrapping the very first admin still needs the existing manual SQL step (`UPDATE profiles SET role_id = 2 WHERE id = ...`, documented in root `README.md`), shown as an inline note in the tab itself.
- **"University" instead of "Place" (#106)**: every user-visible "Place"/"Places" string across `admin_home_screen.dart`, `add_place_screen.dart`, `edit_place_screen.dart`, `add_building_screen.dart`, `capture_screen.dart`, `connect_anchor_points_screen.dart`, and `add_connection_screen.dart` now reads "University"/"Universities" - this deployment's "places" are specifically university campuses. Display-string-only: `place_id`, `/places` API calls, `PlaceCreate`/`PlaceResponse`/`PlaceUpdate` (`backend-map-management`), and `db_schema/places.sql` are all untouched on purpose, since a different deployment of this app might not be organized around universities at all.
- **Multi-language infrastructure (#105)**: Flutter's own official `flutter gen-l10n` (not a third-party i18n package) - `l10n.yaml`, `lib/l10n/app_en.arb`/`app_es.arb` (Colombian Spanish, matching this deployment's real anchor-point data seen during testing - "Bloque 30," "Portería Vegas"), generating `lib/l10n/app_localizations.dart`. **Deliberately partial scope**: fully localized are `lib/auth/` (login/signup/`AuthGate`), `location.dart`/`camera.dart`, and every `lib/user/` screen (`UserHomeScreen`, `NavigationScreen`, `AnchorPointPickerScreen`, the new `SettingsScreen`) plus the new Admin Users tab - the actual user-facing flow, which is what's "about to be tested with Spanish-speaking users" per #105's own problem statement. The older admin CRUD screens (`add_place_screen.dart`/`edit_place_screen.dart`/`add_building_screen.dart`/`edit_building_screen.dart`/`capture_screen.dart`/`capture_photo_screen.dart`/`connect_anchor_points_screen.dart`/`add_connection_screen.dart`/`admin_home_screen.dart`'s own CRUD-tab bodies) stay hardcoded English (University-renamed per #106, just not translated) - #105's own text anticipated exactly this split ("this likely wants its own follow-up translation-content pass... rather than one single giant PR"), tracked as a new follow-up issue rather than silently left incomplete. `MainApp`'s `theme`/`darkTheme` also went from Flutter's bare Material default to a real `ColorScheme.fromSeed`-based theme (needed to have something to swap to `highContrastLight()`/`highContrastDark()` against).

## Complete workflow

1. **App start** — `main()` loads `.env` (falling back to `dotenv.testLoad(fileInput: '')` if missing, e.g. in a test run, so the app doesn't crash without a real `.env`), initializes `Supabase.initialize(...)` with `SUPABASE_URL`/`SUPABASE_PUBLISHABLE_KEY` (falling back to harmless placeholder values if unset — Supabase's client doesn't validate reachability at init time), then `LocationService().initialize()`, then shows `AuthGate`.
2. **`AuthGate`** — if `Supabase.instance.client.auth.currentSession` is null, shows `LoginScreen` (with a link to `SignupScreen`). If signed in, fetches the user's profile and routes to `AdminHomeScreen` or `UserHomeScreen` based on `role_id`. A 404 (no profile row) falls back to `UserHomeScreen`, same as before — but any other failure (backend unreachable, a non-404 error response, a 10s timeout) now shows a distinct error screen with a Retry button instead of silently falling back too (fixed in #115, after a real backend outage during #114 was mistaken for a login bug since the two cases used to look identical).
3. **Sign up** — email/password → Supabase Auth `signUp` → on success, `POST /profiles` with the new user's id. If the profile call fails, the auth account still exists (shown as an error in the UI, not rolled back) — there's no compensating transaction.
4. **`UserHomeScreen`** — *is* the trip-planning flow: a "Start" row (static - always "your current location") and a "Where to?" row that pushes `AnchorPointPickerScreen` for the destination only (Place → Building → anchor drill-down, filtered to `verified`), plus a logout button and a secondary app-bar camera icon into the original raw `SimpleCameraWidget` capture flow (still real, now secondary rather than the default view). Tapping **Find route** fetches every verified anchor point, picks the one nearest `LocationService().lastPosition` via `haversineMeters` as the start, then `POST /route/routes/find_or_create` with that computed start plus the picked end. A 404 ("no walkable path") shows inline; success pushes `NavigationScreen(route: ...)`.
5. **Data-collection capture** (secondary action, not the default screen anymore) — tapping `SimpleCameraWidget`'s button takes a photo, reads `LocationService().lastPosition` and the live `flutter_compass` heading, and POSTs multipart (file field `image` + `latitude`/`longitude`/`accuracy` + optional `heading`) via `DataCollectionApi().postMultipart(...)` to the gateway's `/data-collection/upload`.
7. **`NavigationScreen`** — on entry, `POST /sessions` with the signed-in user's id, the route's `building_id`, its own id as `route_id`, and now `start_position`/`device_info` too; keeps the returned session id in state, starts background camera init, and kicks off the self-rescheduling correction loop described above. Each tick either calls `POST /correct_position` + `POST /logs` (with `corrected_*`/`anchor_match_id`/`confidence_score` populated) or, on any failure, falls back to a raw-GPS-only `POST /logs`. Shows `LocationInfo` (plus a corrected-position text row once available) and `SimpleMapWidget` (plus a second marker once available) while active. On "End navigation": stops the loop, `PATCH /sessions/{id}` with `status: "completed"`/`end_time`/`end_position`, then a dialog offers to `POST /feedback` before popping back. Session-end and tick failures are swallowed (best-effort) rather than blocking the user from leaving the screen.
8. **`AdminHomeScreen`** — fetches `GET /places`/`GET /buildings`/`GET /anchor-points`/`GET /anchor-point-photos`/`GET /anchor-point-connections` and shows them across four of its five tabs (Universities/Buildings/Anchor points/Connections), each searchable, editable (connections excepted), and deletable (cascade-impact-warning dialog first); the floating action button (Add university / Add building / New anchor point / Connect on map) and each row's edit/add-photo actions reload the five lists on return, as does an app-bar refresh icon plus pull-to-refresh. The 5th tab, **Users**, lazily fetches `GET /profiles` on first visit and offers promote/demote. Its drawer also has a "Live sessions" entry into `LiveSessionsScreen`/`SessionTrackingScreen` (see above).
9. **`SettingsScreen`** — reachable from `UserHomeScreen`'s gear icon: verbosity, high contrast, and language, saved to `profiles.preferences` via `PATCH /profiles/{id}` and applied immediately app-wide via `app_preferences.dart`'s notifiers.
11. **`ConnectAnchorPointsScreen`**/**`AddConnectionScreen`** — build the `anchor_point_connections` walkability graph: tap-tap on a map (chain-connecting along a corridor) or a dropdown form with an optional manual distance override. Both `POST /anchor-point-connections`; the backend fills in `distance_meters` via haversine when omitted.
9. **`CaptureScreen`** — a place dropdown (`GET /places`) and a building dropdown (`GET /buildings`, filtered client-side to the selected place), a hardcoded `location_type` dropdown (matching `db_schema/location_type.sql`'s seeded values — no CRUD endpoint exists for that table, same reasoning as the hardcoded role ids), a required description field (doubles as the point's display name), an indoor/outdoor switch, an optional lighting dropdown (bright/moderate/dim), an optional free-text surface field (sent together as `metadata`, capture-condition notes for admin review and the future visual-matching pipeline — see `backend-map-management/CLAUDE.md`), and a "Pick on map" button (`LocationPickerScreen`, scoped to the selected place/building) for when the device's current GPS fix isn't the desired spot. On submit: `POST /anchor-points` with the form fields and the picked or device-GPS position (picked takes priority), then pushes `CapturePhotoScreen` for the new id. `EditAnchorPointScreen` has the same indoor/lighting/surface controls, pre-filled from the fetched anchor point's `metadata` and sent back via `PATCH` alongside its other fields.
10. **`CapturePhotoScreen`** — camera preview + live compass heading ("Facing: N°"), reached either fresh (from `CaptureScreen`, no existing photos) or via `AdminHomeScreen`'s "Add photo" (fetches existing photos first via `GET /anchor-points/{id}/photos`). Each "Take photo" tap uploads via `POST /anchor-points/upload-image` then records it via `POST /anchor-points/{id}/photos` (`image_url`, frozen `heading`, `captured_by` set to `Supabase.instance.client.auth.currentUser!.id`), shown in a thumbnail grid with a per-photo delete (`DELETE /anchor-point-photos/{id}`). "Done" pops back.

### Widget/service internals (unchanged from before)

- `lib/services/location_service.dart` — singleton wrapping `Geolocator`; exposes a broadcast `Stream<Position>` (`positionStream`) and a cached `lastPosition`. Widgets subscribe to the stream independently rather than receiving position via a shared parent widget — follow this pattern (thread through `LocationService`, not widget constructors) for any new widget that needs live position.
- `lib/camera.dart`'s `_sendPhotoToServer` now goes through `DataCollectionApi` (`api_service.dart`), like every other backend call, instead of a hardcoded URL.

## Known gaps
- No dedicated voice/haptic feedback for a correction - today it's just a text row under `LocationInfo` and a second map marker, both silent. A visually-impaired user navigating alone wouldn't actually see either; this is the minimal display, not the final UX for this feature.
- `NavigationScreen` doesn't validate the route has valid `building_id`/anchor references before starting a session, and doesn't handle losing GPS mid-session beyond simply not logging that tick.
- `UserHomeScreen`'s "no walkable path found" case gives the user no way to fix it themselves - the connections graph can only be extended by an admin (`ConnectAnchorPointsScreen`/`AddConnectionScreen`), so a real dead end today just means asking an admin to add a connection.
- The auto-selected start point is purely nearest-by-straight-line-distance - it doesn't check that point is actually reachable (connected in the graph) from the chosen destination before computing a path, so "no walkable path found" can still surface after the start is already picked, with no way to pick a different (farther but connected) start instead.
- `SessionTrackingScreen`'s poll interval (4s) is fixed, not configurable, and keeps polling even if the session ends mid-watch (no server-side push/websocket in this repo - everything is REST poll, consistent with the rest of the app).
- `test/widget_test.dart` is currently just a sanity smoke test so CI has something to run — add real widget/unit tests alongside new widgets/services. A full auth-flow test isn't practical without a mocked Supabase client, so none exists yet.
- **`verbosity` is stored but not yet consumed anywhere** - `SettingsScreen` saves it to `profiles.preferences`, but no screen actually reads it back to change how much on-screen detail it shows. The setting exists ahead of the behavior it's meant to drive.
- **The older admin CRUD screens are not localized** (see #105 above) - a real gap if an admin ever needs the Spanish UI, not just app users. Tracked as a dedicated follow-up rather than silently left out.
- **No real screen-reader semantics anywhere** (#82, unchanged by this round) - icon-only buttons and color-only status indicators still have no `Semantics`/`semanticLabel`. TalkBack/VoiceOver would announce little of value today regardless of the device's language setting.
