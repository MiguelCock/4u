## What this app does

Single Flutter codebase serving two roles from the root README's design: `user` (picks a trip, navigates it, receives a corrected position) and `admin` (captures anchor points/their photos, builds the walkability graph, watches active sessions live). `lib/main.dart` loads `.env` (`flutter_dotenv`), initializes Supabase Auth, and shows `AuthGate` — real login/signup and role branching. `UserHomeScreen` (`lib/user/`) *is* the trip-planning flow now, not a map and not a screen reached via a FAB: the user only picks a destination (`anchor_point_picker_screen.dart`'s Place → Building → anchor-point drill-down) - the start point is auto-selected as the verified anchor point nearest their current GPS fix (`lib/services/geo_utils.dart`'s `haversineMeters`, Uber-pickup-pin style), not picked by hand. There is no flat pre-made route list either; a route is found or computed on the fly between the auto-selected start and the picked destination (`backend-route-management`'s `POST /routes/find_or_create`, real pathfinding over the `anchor_point_connections` graph). The admin side has the original two-step capture flow — `lib/admin/capture_screen.dart` (creates the `anchor_points` row: place/building/type/description/position) then `lib/admin/capture_photo_screen.dart` (the ~4-8-photos-per-point loop) — plus place/building/anchor-point creation/editing, the connections-graph builder, and now `sessions_screen.dart`/`user_sessions_screen.dart`/`session_tracking_screen.dart` for browsing every user's navigation sessions (any status, not just active), watching one's logged trail on a map, and deleting one.

## How it connects to the rest of the system

`lib/services/api_service.dart` gives the app real HTTP clients for every backend service — `UserManagementApi`, `MapManagementApi`, `RouteManagementApi`, `NavigationManagementApi`, `DataCollectionApi` — each built from a single `API_GATEWAY_URL` in `.env` plus its own fixed path prefix (`/user`, `/map`, `/route`, `/navigation`, `/data-collection`), routed by the API gateway (`gateway/nginx.conf`) to the matching backend service. This is a change from before — previously the app read 5 separate base-URL env vars, and `backend-data-collection` wasn't wired through this pattern at all (see Known gaps history).

- **Auth**: `lib/auth/signup_screen.dart` calls Supabase Auth's `signUp`, then `UserManagementApi().post('/profiles', ...)` with the new auth user's id and `role_id: 1` (`user`) — the real trigger for `backend-user-management`'s `POST /profiles` that every service's `CLAUDE.md` previously described as "nothing calls this." `login_screen.dart` calls `signInWithPassword`. Both rely on `AuthGate`'s `Supabase.instance.client.auth.onAuthStateChange` listener to react to the resulting session change, rather than navigating manually.
- **Role routing**: `AuthGate` fetches `GET /profiles/{id}` (`backend-user-management`) for the signed-in user and shows `AdminHomeScreen` if `role_id == 2`, else `UserHomeScreen` — matching `db_schema/roles.sql`'s seeded `user`/`admin` ids (hardcoded as `kUserRoleId`/`kAdminRoleId` rather than fetched, since `roles` has no reason to change at runtime). A 404 here self-heals (see below) rather than just falling back to `UserHomeScreen`.
- **Self-healing a missing profile row (v0.2.1 hotfix)**: a real production account ended up signed up in Supabase Auth with no `profiles` row - `signup_screen.dart`'s `POST /profiles` call failed after the Auth account was already created, and there's no compensating transaction between the two (see "Sign up" below). The account was stuck: `GET`/`PATCH /profiles/{id}` 404 for everything (Settings, admin promotion), and `AuthGate` previously just silently treated that 404 as "not an admin" and moved on, masking the real problem. `AuthGate._fetchProfile` now self-heals on exactly that 404: it calls `POST /profiles` with an empty body (the backend already forces `id`/`role_id` to the verified caller / the default role server-side regardless of what's sent, so nothing else is required) and proceeds with that response as if the original `GET` had succeeded. Any failure in the self-heal `POST` itself still propagates to the existing error+retry screen rather than being swallowed - the same #114/#115 principle of not masking a real failure as a login/role quirk.
- **Data-collection camera removed**: the old raw capture screen (`lib/camera.dart`'s `SimpleCameraWidget`, which uploaded user photos to `backend-data-collection`'s `/upload`) and its app-bar camera icon on `UserHomeScreen` were deleted after field testing, along with their now-unused ARB keys. `DataCollectionApi` and the backend service remain but have no in-app caller.
- **Anchor-point creation and photos**: `lib/admin/capture_screen.dart` only creates the `anchor_points` row (`POST /anchor-points` — `building_id`, `location_type_id`, `latitude`/`longitude`/`altitude`, and a `location_description`, which is its display name. The description is required only for *destination* location types and optional for in-between ones: see "Destinations vs in-between points" below) and, on success, pushes `lib/admin/capture_photo_screen.dart` with the new id. That screen is the real client for `POST /anchor-points/upload-image` (via `MapManagementApi.postMultipart`) and `POST /anchor-points/{id}/photos` — each photo carries its own `heading` (live compass reading, frozen at capture time) and `captured_by` (the signed-in admin's id), since one physical point typically gets ~4-8 photos facing different directions (see `backend-map-management/CLAUDE.md`'s anchor-points/photos schema split). It shows a thumbnail grid of photos taken so far (existing ones fetched via `GET /anchor-points/{id}/photos`, so it also works for adding photos to an already-captured point), each deletable (`DELETE /anchor-point-photos/{id}`). `admin_home_screen.dart` fetches `GET /places`, `GET /buildings`, `GET /anchor-points`, `GET /anchor-point-photos`, and `GET /anchor-point-connections` together for its four tabs (see below).
- **Admin home tabs, search, edit, delete**: `admin_home_screen.dart` is a 4-section screen — Places / Buildings / Anchor points / Connections — navigated via a side `Drawer` (hamburger icon, auto-added by `Scaffold` once a `drawer:` is set) rather than a top `TabBar`; the AppBar title reflects whichever section is active. Internally it's still a `TabController`/`TabBarView` (swipe disabled via `NeverScrollableScrollPhysics` now that the tab indicator isn't visible) — the drawer's `ListTile`s just call `_tabController.animateTo(index)` and close themselves, so `_fab()`'s per-section switch, the Connections-only "Add connection" AppBar action, and the drill-down `animateTo()` calls described below all keep working unchanged. Each section has a client-side search field (by name for places/buildings, by either endpoint's description for anchor points/connections) and a per-row Edit action into `edit_place_screen.dart`/`edit_building_screen.dart`/`edit_anchor_point_screen.dart` (`PATCH` counterparts of the `Add*Screen`s, pre-filled — connections have no edit, delete-and-recreate instead). Anchor-point rows also show a thumbnail (first photo, if any), a photo count, and an "Add photo" action straight into `capture_photo_screen.dart`. Delete (`DELETE /places/{id}`, `/buildings/{id}`, `/anchor-points/{id}`, `/anchor-point-connections/{id}`) is behind a confirmation dialog that states the real cascade impact — counts of buildings/anchor points/photos/connections that will also be deleted — computed client-side from the five already-loaded lists, since `places`→`buildings`→`anchor_points`→(`anchor_point_photos`, `anchor_point_connections`) are all `ON DELETE CASCADE`. The floating action button swaps per active tab (Add place / Add building / New anchor point / Connect on map); the Connections tab also gets a secondary app-bar action ("Add connection (form)") into `add_connection_screen.dart`. A `RefreshIndicator` and an app-bar refresh button reload all five lists. The Anchor points tab also has a status filter (`ChoiceChip`s: All/Pending/Verified/Rejected, each showing a count) above the search field — this is the "pending-review queue," composing with the existing description search rather than replacing it. Tapping a place row (not its Edit/Delete icons) drills down: it sets `_buildingsPlaceFilterId` and switches to the Buildings tab, which then layers a `place_id` filter on top of (not instead of) its own text search, shown as a clearable `InputChip` ("Buildings in <place>") — the same `place_id`/`building_id` scoping `LocationPickerScreen`'s `buildingsPlaceId`/`anchorPointsBuildingId` params already use elsewhere, just applied to this screen's own tabs. Tapping a building row does the same one level down: sets `_anchorPointsBuildingFilterId` and switches to the Anchor points tab, layering a `building_id` filter on top of (not instead of) its existing status chips and description search, shown as its own clearable `InputChip` ("Anchor points in <building>"). `_loadData()` clears either stale scope if the scoped place/building no longer exists after a refresh. The four lists behind a FAB have 88px of bottom padding, so the FAB no longer covers the last row's delete/edit buttons. Empty and error states use `ScrollableMessage` (`lib/widgets/scrollable_message.dart`), so pull-to-refresh works on them too, and pulling also reloads Users once that tab has been opened. Unnamed points are shown everywhere in admin as `anchorDisplayName` (`capture_screen.dart`): their type plus a 4-character id prefix, e.g. "Hallway · 3f2a", never a bare UUID.
- **System back on the root screens**: `AdminHomeScreen` and `UserHomeScreen` are `AuthGate`'s child, not pushed routes, so a bare system back used to close the app. Admin keeps a stack of visited tabs (`_tabHistory`). Back first returns to the previous tab, clearing the drill-down filter of the tab being left; then it clears a remaining filter; then it goes to the first tab. Only then does `ExitGuard` (`lib/services/exit_guard.dart`) show "Press back again to exit", and a second back within 2s exits. `UserHomeScreen` uses the same guard, except in the admin's "Test as user" preview, which is a pushed route and just pops.
- **Destinations vs in-between points**: `lib/services/destinations.dart`'s `kDestinationLocationTypes` holds the location types users can navigate *to*: entrance, classroom, office, restroom, cafeteria, parking, lobby, auditorium and bus stop. It is mirrored by `DESTINATION_LOCATION_TYPE_IDS` in `backend-map-management/app/models.py`, and a backend test fails if the two drift apart. Those types require a description, enforced in `CaptureScreen`/`EditAnchorPointScreen` and again server-side. Other types (hallway, intersection, stairs…) may be saved unnamed, and the helper text says which rule applies. The create form defaults to *hallway*, since most points added while filling in a route are in-between ones. `AnchorPointPickerScreen` lists only verified points of a destination type *with* a name (`isDestinationAnchor`), and hides universities/buildings that have none, so the user's list is just real places. The start point can still be any verified point, including an unnamed one: the Start row describes it by distance (`homeStartUnnamedSubtitle`).
- **Re-index verified points** (admin drawer): re-sends every verified point that has photos to `backend-ai-training`'s `/index_anchor` and reports N of M. It exists because points verified while indexing was failing were never searchable. That failure was the ai-training container's own Supabase credentials, reported as a 401 "session expired" until `packages`' `get_caller_id` started returning 503 for non-token failures. The payload builder is shared with the edit screen and the add-photo flow (`lib/services/anchor_indexing.dart`).
- **Map pins point at their coordinate**: `locationPinMarker` (`lib/map.dart`) sizes `Icons.location_pin` to 40px and aligns its *tip*, not its centre, to the point via `Marker.computePixelAlignment`. The centred version drew the tip ~17px south, so pins never lined up with route lines or anchor dots, and points picked by aiming the tip were saved too far north. `LocationPickerScreen`'s university/building icons are centred in their `Stack` for the same reason.
- **Connect map taps** (`ConnectAnchorPointsScreen`): the per-marker `GestureDetector`s were replaced by `MapOptions.onTap`, which selects the nearest visible point within 32 logical px of the tap. Double-tap zoom is off on this screen, so flutter_map fires taps with no ~300ms wait for a possible second tap. Pinch still zooms. Selection vibrates (`HapticFeedback.selectionClick`). Connecting is optimistic: the line appears (dotted grey) and the selection moves on immediately, and the line is replaced by the saved row or removed on failure. Only the same pair is held back while saving, so chaining along a corridor never drops taps. Tapping an already-connected pair just moves the selection.
- **Voice destination search** (`UserHomeScreen`): a large "Say where you want to go" button listens with `speech_to_text` (Android's recognizer). It needs the `RECORD_AUDIO` permission plus a `<queries>` entry for `RecognitionService`; the manifest also gained one for `TTS_SERVICE`, which Android 11+ package visibility wants for `flutter_tts`.
  - **Language**: it listens in the app language's locale, es-CO first, the same candidates as the voice.
  - **Matching**: `lib/services/destination_matcher.dart` matches the phrase against the destination list only (`isDestinationAnchor`, minus the start point). It's pure and unit-tested: accent- and case-insensitive token overlap that drops filler words in English and Spanish ("quiero ir a la…"). A 4+ letter prefix counts ("cafe" matches "cafetería"), numbers must match exactly (301 ≠ 302), and building-name words help tell same-named places apart. Naming only a building chooses nothing.
  - **Result**: a clear winner (at least 0.25 ahead of the runner-up) becomes the destination, and the app says "Destination: X. Tap Find route to start." Several matches open a bottom sheet with the top three, which are also spoken. No match says what was heard and points to the list.
  - **Feedback**: results go to a live-region status line. They're also spoken with TTS, unless TalkBack is on (`MediaQuery.accessibleNavigation`), which already reads the live region, so it isn't heard twice.
- **Delete connections on the map** (`ConnectAnchorPointsScreen`): a tap that isn't near a point is checked against connection lines in screen space (`_distanceToSegment`, 16px radius). A hit asks for confirmation and then calls `DELETE /anchor-point-connections/{id}`. `backend-route-management`'s `find_or_create` re-checks cached routes against the current connections and recomputes any route through a deleted one.
- **Navigation voice language**: `configureTts` (`lib/services/speech_voice.dart`) picks the TTS voice from the *app* language (`Localizations.localeOf`), not the phone's default. It prefers es-CO, then es-US/es-MX/es-ES (or en-US/en-GB), and offline voices over network ones. With the phone in English and the app in Spanish, Spanish text used to be read with an English accent. If no voice for the language is installed, a SnackBar explains how to add one. It also sets Android's queue mode to *add*, so polite announcements queue instead of cutting each other off. `_speak` waits until the voice is configured.
- **Building↔university reassignment, create-screen pre-selection, scoped status counts**: three small admin-UX fixes found during a round of hands-on testing. `edit_building_screen.dart` gained a university `DropdownButtonFormField` (same `/places` fetch `add_building_screen.dart` already does), pre-selected to the building's current `place_id` and included in the `PATCH /buildings/{id}` payload - `backend-map-management`'s `BuildingUpdate` model previously didn't even declare `place_id`, so a client sending it was silently dropped by Pydantic before this. `AddBuildingScreen`/`CaptureScreen` both gained optional `initialPlaceId`/`initialBuildingId` constructor params, passed by `admin_home_screen.dart`'s `_fab()` from whichever place/building filter is currently active (`_buildingsPlaceFilterId`/`_anchorPointsBuildingFilterId`) - previously "Add building"/"New anchor point" always defaulted to the *first* place/building in the fetched list regardless of what the admin was already looking at. `_statusFilterChips()` now takes the building-scoped anchor-point list as a param instead of counting from the full unscoped `_anchorPoints` - drilling into one building's anchor points used to show status counts (e.g. "Verified (47)") for the whole dataset, not that building.
- **Anchor-point verification**: `edit_anchor_point_screen.dart` now shows a read-only horizontal thumbnail strip of the point's photos (fetched via `GET /anchor-points/{id}/photos`, same call `capture_photo_screen.dart` makes) plus a "Manage photos" button into `CapturePhotoScreen` — an admin reviewing whether to set `status` to `verified`/`rejected` has something to actually look at instead of judging from lat/lng/description alone. `LocationPickerScreen`'s anchor-point markers are now color-coded by `status` (green/grey/red for verified/pending/rejected) instead of a flat green dot, so verified points are visually distinct on every screen that overlay appears on (`CaptureScreen`, `AddBuildingScreen`/`EditBuildingScreen`, `EditAnchorPointScreen`'s own "Move on map"). `connect_anchor_points_screen.dart` has its own separate marker rendering for building the connections graph and isn't part of this.
- **Qdrant indexing on verify**: `lib/services/api_service.dart`'s `AiTrainingApi` (prefix `/ai-training`) is the real client for `backend-ai-training`'s `POST /index_anchor` — right after `edit_anchor_point_screen.dart`'s `PATCH` succeeds with `status: 'verified'`, it posts the anchor point's id/position/building plus its already-loaded `_photos` (id/image_url/heading, no extra fetch) so only confirmed-good anchor points enter the Qdrant-searchable index. If indexing fails, the screen stays open with an inline error instead of popping (the verify itself already saved) — re-tapping Save safely retries, since indexing upserts by photo id are idempotent. Saving an already-verified point (e.g. just to move it) re-indexes all its current photos too, refreshing the stored coordinates. Saving with any **other** status (moving a point back to `pending`, or to `rejected`) instead calls `DELETE /index_anchor/{id}` — best-effort, doesn't block saving — so a downgraded point actually leaves the searchable index instead of just no longer being re-indexed.
- **Keeping Qdrant in sync afterward**: `capture_photo_screen.dart` fetches the anchor point's own record (`GET /anchor-points/{id}`) alongside its photos so it knows whether the point is already verified — adding a photo there indexes just that one new photo when it is (`POST /index_anchor` with a single-item `photos` list), and deleting a photo there always calls `DELETE /index_photo/{id}` on `backend-ai-training` (harmless no-op if it was never indexed). `admin_home_screen.dart`'s three cascade-delete handlers (place/building/anchor point) each call a matching Qdrant cleanup endpoint (`DELETE /index_anchor/{id}` or `/index_building/{id}`, looped over every affected building for a place) before the Postgres delete — wrapped in a `_bestEffort` helper that swallows `ApiException` internally, since a stray Qdrant failure shouldn't block a delete the admin already confirmed.
- **Anchor-point connections (walkability graph)**: `connect_anchor_points_screen.dart` is the primary way to build the graph — a place/building-filtered `flutter_map` showing every anchor point as a tappable marker (existing connections between visible points drawn as green `Polyline`s), where tapping one point then another calls `POST /anchor-point-connections` (`created_by` = signed-in admin id, `distance_meters` omitted so the backend computes straight-line distance) and leaves the just-tapped point selected so a corridor can be chain-connected point by point without re-entering the flow. `add_connection_screen.dart` is the dropdown-based fallback (place → optional building filter → anchor point A/B dropdowns → optional distance override/notes) for when precision matters more than speed, or the admin isn't near a map. Neither screen pre-checks for an existing connection before posting — a duplicate (in either id order) is caught by the backend's `UNIQUE` constraint and surfaces as a generic "already connected" snackbar message, not a hard block.
- **Place/building creation**: `admin_home_screen.dart`'s per-tab FAB opens `lib/admin/add_place_screen.dart` (`POST /places`) and `lib/admin/add_building_screen.dart` (`POST /buildings`, with a place dropdown from `GET /places`) — closes the gap where `places`/`buildings` had to be seeded by hand in Supabase before an admin could capture any anchor point.
- **Map-pin location picking**: `lib/admin/location_picker_screen.dart` is a reusable `flutter_map` screen (same tile setup as `map.dart`) that pops a tapped `LatLng` back to its caller — used by `add_place_screen.dart`/`edit_place_screen.dart`, `add_building_screen.dart`/`edit_building_screen.dart`, `capture_screen.dart` (a nullable `_pickedPosition` that takes priority over `LocationService().lastPosition` at submit time, and relaxes the old "GPS required" guard to accept either a GPS fix or a manual pick), and `edit_anchor_point_screen.dart` ("Move on map"). This closes the map-pin-picker half of what was tracked as GitHub issue #37. Its app-bar "Confirm" action is an `IconButton` (a checkmark), not a `TextButton` with a hardcoded text color — an earlier version used white text on a light AppBar and was effectively invisible.
- **Existing-data overlay on the picker**: `LocationPickerScreen` optionally fetches and overlays existing places (`Icons.flag`, purple, badged with their building count)/buildings (`Icons.apartment`, orange, badged with their anchor-point count)/anchor points (plain green dot — heading now lives per-photo, not on the anchor point itself, so it's no longer meaningful to show on this overlay) via `showPlaces`/`showBuildings`/`showAnchorPoints` flags, self-fetching via its own `MapManagementApi()` rather than requiring callers to pre-fetch. `buildingsPlaceId`/`anchorPointsBuildingId` scope the buildings/anchor-points overlays to one place/building (`CaptureScreen`/`AddBuildingScreen`/`EditBuildingScreen` pass these so the map only shows what's actually relevant to the form being filled in, not every building or anchor point in the system). Lets an admin see duplicates/coverage gaps while picking a new location.
- **Anchor-point-photo heading**: `capture_photo_screen.dart` captures a real compass heading (`flutter_compass`, magnetometer-based — `geolocator`'s `Position.heading` is GPS course-over-ground and meaningless while standing still to photograph a fixed point) via `FlutterCompass.events`, shown live over the camera preview ("Facing: N°") and frozen at the moment each photo is taken (not at submit time, since the admin could reorient between photos). Sent as `heading` in the `POST /anchor-points/{id}/photos` payload. No Android manifest changes needed (location permissions flutter_compass also wants are already declared for `geolocator`); no `ios/` directory exists in this project.
- **Tile source**: `lib/services/map_tile_config.dart` holds the one `TileLayer` URL/user-agent both `map.dart` and `location_picker_screen.dart` use — the official `tile.openstreetmap.org`, not the OpenStreetMap France "hot" mirror this used to point at, which started rejecting requests from the app under its own usage policy (served a "does not respect ... base map usage policy" placeholder image instead of real tiles). Note OSM.org's own tile server also discourages heavy/production use — fine for now, but a real deployment should eventually move to a committed provider with an API key (MapTiler, Stadia Maps, etc.).
- **Trip planning**: `lib/user/user_home_screen.dart` ("Where to?") is the real client for `backend-route-management`'s `POST /routes/find_or_create` — the Uber-style replacement for both a flat pre-made route list (`route_list_screen.dart`, removed) and an earlier version of this screen that made the user pick both a start and an end point (`plan_trip_screen.dart`, also removed - folded directly into `UserHomeScreen` once the start point became auto-selected, since there was no longer a second screen's worth of UI left to justify). It pushes `anchor_point_picker_screen.dart` once, for the destination only - a Place → Building → anchor-point drill-down (three sequential list steps inside one `StatefulWidget`, not three separate pushed screens, so going "back" from the anchor-point step returns to the building step rather than exiting the whole picker; anchor points are filtered to `status == 'verified'`, since an unverified point has no indexed photos and isn't a trustworthy destination for the correction pipeline). The start point is computed client-side: fetch every verified anchor point, pick the one with the smallest `haversineMeters` distance (`lib/services/geo_utils.dart`) to `LocationService().lastPosition`. Submitting calls `find_or_create` with that computed start plus the picked end, which either returns an existing route for that exact `(start, end)` pair or computes a new one via Dijkstra over `anchor_point_connections` (see `backend-route-management/CLAUDE.md`) - a 404 ("no walkable path") is shown inline rather than silently failing, since the connections graph is hand-built by admins and may simply not cover that pair yet. On success it pushes `navigation_screen.dart` with the resulting route.
- **Navigation session lifecycle**: `navigation_screen.dart` is the real client for `backend-navigation-management`: `POST /sessions` on start (now also sending `start_position`/`device_info`, previously always omitted), `PATCH /sessions/{id}` on end, and an optional `POST /feedback` from a post-session dialog.
- **Admin session browser**: `lib/admin/sessions_screen.dart` (renamed from `live_sessions_screen.dart` - no longer active-only) fetches **all** sessions regardless of status (`GET /navigation/sessions`) plus `GET /user/profiles` once, groups sessions by `user_id` client-side (same "fetch all, group/filter client-side" convention as everywhere else), and lists one row per user with a session (name, total count, an "active" badge if any are still running). Tapping a user pushes `lib/admin/user_sessions_screen.dart`, that user's full session history (newest first, with its route's name resolved via a once-fetched `GET /route/routes` lookup), each row offering a **Watch** action into `session_tracking_screen.dart` (works for any status - a non-active session just shows its final static trail, since nothing is still being logged) and a **Delete** action (confirmation dialog, then `DELETE /navigation/sessions/{id}` - a new endpoint, admin-only, that detaches any linked `user_feedback` row's `session_id` before deleting, since that FK has no cascade rule; `navigation_logs` cascades automatically and needs no code here - see `backend-navigation-management/CLAUDE.md`). `session_tracking_screen.dart` itself polls `GET /navigation/logs` every ~4s (a repeating `Timer`, not a single fetch), filters client-side to that `session_id`, sorts by `timestamp`, and draws the **full trail** (a `Polyline` through every logged point so far, using `corrected_lat`/`corrected_long` when a tick has them else raw `gps_lat`/`gps_long`) plus a marker at the latest point - a dedicated `FlutterMap` here rather than reusing `SimpleMapWidget`, since this view has no live-GPS-stream concept, just historical data. It also fetches the session's route (`GET /route/routes/{id}` then each anchor's lat/lng via `GET /map/anchor-points/{id}`) and overlays the *planned* path in a second color, so an admin can visually compare the intended route against what was actually logged - directly useful for testing the correction pipeline, which is the scenario this screen exists for.
- **Guidance line on the live navigation map (#41, #36)**: `map.dart`'s `SimpleMapWidget` gained a `plannedPath` param (`List<LatLng>`, default `[]`, additive alongside `extraMarkers`) rendered as a blueGrey `PolylineLayer` - the same color convention `session_tracking_screen.dart`'s planned-path overlay already uses. `navigation_screen.dart` resolves it in `_loadPlannedPath()`: `widget.route`'s `start_anchor_id`/`waypoint_anchor_ids`/`end_anchor_id` (already in hand from `find_or_create`, no re-fetch of the route itself needed) → one `GET /map/anchor-points/{id}` per id → a `LatLng` list, best-effort (a missing/deleted anchor just means no line, never blocks navigation).
- **Non-visual feedback (#39, #40, #83)**: `navigation_screen.dart` speaks with `flutter_tts` at meaningful moments only, never on every ~1s correction tick, which would be unusable. It's gated by the `voice_guidance` boolean in `profiles.preferences` (`app_preferences.dart`'s `voiceGuidanceNotifier`, default on), toggleable in `SettingsScreen`. A short `HapticFeedback.selectionClick()` fires once per *newly* matched anchor point (`_lastHapticAnchorId`), not every tick that re-confirms the same match.
- **Turn-by-turn guidance**: the app tells the user which way to face, how far to turn, and when to start walking. The decisions are pure and unit-tested in `lib/services/turn_guidance.dart`; the screen supplies inputs and speaks the cues.
  - **Inputs**: a smoothed `flutter_compass` heading (`HeadingSmoother`, a circular moving average, so 359→1 doesn't average to 180). GPS direction of travel is the fallback, used only above 0.7 m/s. Position is the camera-corrected one while it's under 5s old, raw GPS otherwise. Bearings come from `geo_utils.dart`'s `bearingDegrees`/`signedTurn`.
  - **State machine** (`TurnGuidance`), evaluated every 500ms by `_guide`, independently of the slower camera loop:
    - *Orienting*: more than 25° off means "Turn left/right about N degrees", rounded to 15°, or "turn around" above 150°. It repeats when the needed turn changes by more than 20° (at least 4s apart), or every 10s if nothing changes.
    - *Aligned*: within 20° for 1.5s means "You're facing the right way. Start walking forward, N meters", then the state switches to *walking*.
    - *Walking*: quiet, unless the user is more than 45° off for 3s, which goes back to orienting.
  - **Waypoints**: reaching any upcoming waypoint within 20m counts, so a noisy fix that skips past a point doesn't stall guidance. At an intermediate waypoint, one sentence gives the next leg: "Turn left about 45 degrees, then walk 12 meters" or "Continue straight for 20 meters", using the leg's length. Only named destination-type points are spoken, as "At the cafeteria, …". Unnamed hallway points are never named, and no id is ever spoken.
  - **Start and arrival**: the trip starts with "Starting route to {destination}", using the destination's own name rather than the backend's English "A to B" route name. Reaching the last waypoint says "You have arrived at {destination}. Navigation finished." and ends the session by itself (`_endSession(arrived: true)`: `PATCH completed`, then the feedback dialog). The End button is still there for stopping early.
  - **Periodic update**: "{n} meters ahead" every 25s, only while walking and only if nothing was said in the last 10s, so it never piles onto a turn instruction.

- **Position correction tick**: `navigation_screen.dart` also now drives `backend-positioning`'s `POST /correct_position` (via a new `PositioningApi`, prefix `/positioning`) — its first real caller. Not a `Timer.periodic`: a self-rescheduling loop (`_runTick`) fires once, then schedules the next run 1s after the *current one finishes* rather than 1s after it started, so a slow round-trip (camera shutter + CNN embedding + Qdrant search, ~600ms-1s per #122) can't cause ticks to overlap or queue up for the same session. Each tick captures a live frame via a background `CameraController` (same init pattern as `SimpleCameraWidget` in `lib/camera.dart` - `Permission.camera.request()` → `availableCameras()` → `CameraController(..., ResolutionPreset.medium)`), posts it with the current GPS fix, then forwards the response's `corrected_lat`/`corrected_long`/`correction_error`/`anchor_match_id`/`confidence_score` straight into the same `POST /logs` call alongside the raw `gps_*` fields - no reshaping needed, `backend-positioning/CLAUDE.md` documents the response as deliberately shaped for this hand-off. Any failure in this path (camera permission denied/unavailable, `/correct_position` unreachable or slow, auth rejected) degrades to the old raw-GPS-only `POST /logs` call for that tick - never blocks navigation. The camera preview itself is never shown in a release build (`kDebugMode`-gated, `package:flutter/foundation.dart`) since the primary user is visually impaired; in a debug build it appears as a small corner overlay so a developer can sanity-check what's being captured. `map.dart`'s `SimpleMapWidget` gained an `extraMarkers` param (default `[]`, additive) so this screen can show a second, green pin at the corrected position alongside the existing blue live-GPS one. The correction tick is also geo-scoped now: `_correctionTick` forwards the live GPS fix's `latitude`/`longitude` to `/correct_position`, which `backend-positioning` in turn forwards to `backend-ai-training`'s `/search_similar` as a `GeoRadius` filter (see `backend-positioning/CLAUDE.md`) instead of matching against every indexed anchor point regardless of distance.
- **Camera-use transparency and blocked-camera detection**: `_startSession`'s success path speaks (politely) and shows a `SnackBar` stating the camera will be used periodically, every time navigation starts - deliberately said every time rather than once-ever, so there's no persisted "already told them" flag to get out of sync. Each correction tick's captured frame is checked by `lib/services/image_utils.dart`'s `isFrameBlocked` (decoded at a small fixed 32×32 size to bound CPU cost given #122's existing latency concerns) before upload - a cheap brightness/variance heuristic (v1, meant to be benchmarked on-device, not a polished solution): a frame reads as blocked if its mean luma is very low (near-black, e.g. a lens cap or a finger) *or* its luma standard deviation is very low regardless of mean (a flat, textureless frame, e.g. a lens pressed against a bright surface). Debounced over `_kCameraBlockedDebounceTicks` (3) consecutive ticks so one dim hallway or a brief motion blur doesn't false-positive, and announced only once per blocked streak (`_blockedAnnounced`) rather than every tick. The announcement is assertive (interrupts whatever's queued, see `_speak`'s doc comment) and - like the camera disclosure - both spoken and shown as a `SnackBar`. A blocked tick still logs the raw GPS fix via `_logRawTick`, it just skips the `/correct_position` upload for that tick.

## Complete workflow

1. **App start** — `main()` loads `.env` (falling back to `dotenv.testLoad(fileInput: '')` if missing, e.g. in a test run, so the app doesn't crash without a real `.env`), initializes `Supabase.initialize(...)` with `SUPABASE_URL`/`SUPABASE_PUBLISHABLE_KEY` (falling back to harmless placeholder values if unset — Supabase's client doesn't validate reachability at init time), then `LocationService().initialize()`, then shows `AuthGate`.
2. **`AuthGate`** — if `Supabase.instance.client.auth.currentSession` is null, shows `LoginScreen` (with a link to `SignupScreen`). If signed in, fetches the user's profile and routes to `AdminHomeScreen` or `UserHomeScreen` based on `role_id`. A 404 (no profile row) self-heals by creating one on the spot (v0.2.1 - see "Self-healing a missing profile row" above) — but any other failure (backend unreachable, a non-404 error response, a 10s timeout, or the self-heal `POST` itself failing) still shows a distinct error screen with a Retry button instead of silently falling back (originally fixed in #115, after a real backend outage during #114 was mistaken for a login bug since the two cases used to look identical).
3. **Sign up** — email/password → Supabase Auth `signUp` → on success, `POST /profiles` with the new user's id. If the profile call fails, the auth account still exists (shown as an error in the UI, not rolled back) — there's no compensating transaction here still, but `AuthGate` now repairs the gap the next time that account signs in (v0.2.1).
4. **`UserHomeScreen`** — *is* the trip-planning flow: a "Start" row (static - always "your current location") and a "Where to?" row that pushes `AnchorPointPickerScreen` for the destination only (Place → Building → anchor drill-down, filtered to `verified`), plus a logout button. The picker lists destinations only (see "Destinations vs in-between points"). Tapping **Find route** fetches every verified anchor point, picks the one nearest `LocationService().lastPosition` via `haversineMeters` as the start, then `POST /route/routes/find_or_create` with that computed start plus the picked end. A 404 ("no walkable path") shows inline; success pushes `NavigationScreen(route: ...)`.
7. **`NavigationScreen`** — on entry, `POST /sessions` with the signed-in user's id, the route's `building_id`, its own id as `route_id`, and now `start_position`/`device_info` too; keeps the returned session id in state, starts background camera init, and kicks off the self-rescheduling correction loop described above. Each tick either calls `POST /correct_position` + `POST /logs` (with `corrected_*`/`anchor_match_id`/`confidence_score` populated) or, on any failure, falls back to a raw-GPS-only `POST /logs`. Shows `LocationInfo` (plus a corrected-position text row once available) and `SimpleMapWidget` (plus a second marker once available) while active. On "End navigation": stops the loop, `PATCH /sessions/{id}` with `status: "completed"`/`end_time`/`end_position`, then a dialog offers to `POST /feedback` before popping back. Session-end and tick failures are swallowed (best-effort) rather than blocking the user from leaving the screen.
8. **`AdminHomeScreen`** — fetches `GET /places`/`GET /buildings`/`GET /anchor-points`/`GET /anchor-point-photos`/`GET /anchor-point-connections` and shows them across four of its five tabs (Universities/Buildings/Anchor points/Connections), each searchable, editable (connections excepted), and deletable (cascade-impact-warning dialog first); the floating action button (Add university / Add building / New anchor point / Connect on map) and each row's edit/add-photo actions reload the five lists on return, as does an app-bar refresh icon plus pull-to-refresh. An app-bar gear icon opens the same `SettingsScreen` the user side uses. The 5th tab, **Users**, lazily fetches `GET /profiles` on first visit and offers promote/demote. Its drawer also has a "Sessions" entry into `SessionsScreen`/`UserSessionsScreen`/`SessionTrackingScreen` (see above).
9. **`SettingsScreen`** — reachable from a gear icon on both `UserHomeScreen` and `AdminHomeScreen`: verbosity, high contrast, language, and font size, saved to `profiles.preferences` via `PATCH /profiles/{id}` and applied immediately app-wide via `app_preferences.dart`'s notifiers.
11. **`ConnectAnchorPointsScreen`**/**`AddConnectionScreen`** — build the `anchor_point_connections` walkability graph: tap-tap on a map (chain-connecting along a corridor) or a dropdown form with an optional manual distance override. Both `POST /anchor-point-connections`; the backend fills in `distance_meters` via haversine when omitted.
9. **`CaptureScreen`** — a place dropdown (`GET /places`) and a building dropdown (`GET /buildings`, filtered client-side to the selected place), a hardcoded `location_type` dropdown (matching `db_schema/location_type.sql`'s seeded values — no CRUD endpoint exists for that table, same reasoning as the hardcoded role ids), a required description field (doubles as the point's display name), an indoor/outdoor switch, an optional lighting dropdown (bright/moderate/dim), an optional free-text surface field (sent together as `metadata`, capture-condition notes for admin review and the future visual-matching pipeline — see `backend-map-management/CLAUDE.md`), and a "Pick on map" button (`LocationPickerScreen`, scoped to the selected place/building) for when the device's current GPS fix isn't the desired spot. On submit: `POST /anchor-points` with the form fields and the picked or device-GPS position (picked takes priority), then pushes `CapturePhotoScreen` for the new id. `EditAnchorPointScreen` has the same indoor/lighting/surface controls, pre-filled from the fetched anchor point's `metadata` and sent back via `PATCH` alongside its other fields.
10. **`CapturePhotoScreen`** — camera preview + live compass heading ("Facing: N°"), reached either fresh (from `CaptureScreen`, no existing photos) or via `AdminHomeScreen`'s "Add photo" (fetches existing photos first via `GET /anchor-points/{id}/photos`). Each "Take photo" tap uploads via `POST /anchor-points/upload-image` then records it via `POST /anchor-points/{id}/photos` (`image_url`, frozen `heading`, `captured_by` set to `Supabase.instance.client.auth.currentUser!.id`), shown in a thumbnail grid with a per-photo delete (`DELETE /anchor-point-photos/{id}`). "Done" pops back.

### Widget/service internals (unchanged from before)

- `lib/services/location_service.dart` — singleton wrapping `Geolocator`; exposes a broadcast `Stream<Position>` (`positionStream`) and a cached `lastPosition`. Widgets subscribe to the stream independently rather than receiving position via a shared parent widget — follow this pattern (thread through `LocationService`, not widget constructors) for any new widget that needs live position.

## Known gaps
- Voice/haptic feedback now exists (see "Non-visual feedback" above), and a follow-up pass added `Semantics(liveRegion: true, ...)` around every dynamic error/status `Text` in the user-facing flow (`login_screen.dart`, `signup_screen.dart`, `user_home_screen.dart`, `anchor_point_picker_screen.dart`, `settings_screen.dart`, `location.dart`'s GPS-error row, `camera.dart`'s permission/init error, and `navigation_screen.dart`'s session-start error) so TalkBack announces a state change on its own, not only through the app's own TTS. Every icon-only control in these screens already had a `tooltip` from the earlier #82 fix or Flutter's own `MaterialLocalizations` (the `AppBar` back button) - the remaining gap was specifically live-region announcement of text that changes after the screen has already built, not missing labels. Deliberately **not** made a live region: `navigation_screen.dart`'s corrected-position row, which updates on every ~1s correction tick - wrapping that would spam TalkBack with an announcement a second, duplicating the existing arrival/proximity TTS and haptics that are already paced for a non-visual audience. Admin screens (operated by sighted staff) remain a deliberate, lower-priority follow-up, same reasoning as the original #82 fix.
- The covered-camera announcement (see "Camera-use transparency" above) follows the same spoken-plus-visible convention as every other announcement: `_speak(..., assertive: true)` plus a `SnackBar` showing the same text, so a user who can't hear it (or has sound off) still sees it.
- **Turn guidance needs on-device tuning**: the thresholds in `TurnGuidance` (25°/20°/45°, 1.5s/3s holds, 4s/10s repeats) and the 20m waypoint radius are first guesses that worked in unit tests, not values tuned on campus. Compass accuracy also varies by phone and near metal structures. If instructions feel too chatty or too slow, these constants are the place to adjust.
- `NavigationScreen` doesn't validate the route has valid `building_id`/anchor references before starting a session, and doesn't handle losing GPS mid-session beyond simply not logging that tick.
- `UserHomeScreen`'s "no walkable path found" case gives the user no way to fix it themselves - the connections graph can only be extended by an admin (`ConnectAnchorPointsScreen`/`AddConnectionScreen`), so a real dead end today just means asking an admin to add a connection.
- The auto-selected start point is nearest-by-straight-line-distance (from a camera-corrected position when one is available, see above) - it doesn't check that point is actually reachable (connected in the graph) from the chosen destination before computing a path, so "no walkable path found" can still surface after the start is already picked, with no way to pick a different (farther but connected) start instead.
- `SessionTrackingScreen`'s poll interval (4s) is fixed, not configurable, and keeps polling even if the session ends mid-watch (no server-side push/websocket in this repo - everything is REST poll, consistent with the rest of the app).
- `test/widget_test.dart` is currently just a sanity smoke test so CI has something to run — add real widget/unit tests alongside new widgets/services. A full auth-flow test isn't practical without a mocked Supabase client, so none exists yet.
- **`verbosity` is stored but not yet consumed anywhere** - `SettingsScreen` saves it to `profiles.preferences`, but no screen actually reads it back to change how much on-screen detail it shows. The setting exists ahead of the behavior it's meant to drive.
